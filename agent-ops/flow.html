’crowagent-opsDesign only, not active

Continuous development with parallel AI agents

Agent ops is a pipeline that lets AI agents change the ’crow codebase continuously. It takes work from four sources, turns each item into a task, runs up to three tasks in parallel, and checks every change with automated tests and with models from two AI companies before it merges. One source is feedback that the operator requests from agents at key deal milestones. The pipeline is not active. Rafa activates it in nine steps.

Summary

What it does

Agent ops turns tickets, agent feedback, the roadmap and usage data into small tasks. Agents build the tasks in parallel. The pipeline merges each change after it passes its checks.

Why it exists

Agents merged 40 pull requests in two days (measured). Coordination and review now limit throughput, not code generation.

How it stays safe

Automated checks run before any model review. A model from a second AI company reviews every critical change. Rafa controls deploys, keys, money, repository settings and changes to the pipeline itself.

What Rafa decides

Rafa decides when to activate the pipeline. Activation has nine steps, listed under Activation.

Pipeline

Every change goes through the same nine stages. Each dot in the animation is a task, and its color shows the task's risk tier.

IncomingCodeCriticalControl

    1. 0

      Intake

      The pipeline collects work from tickets, agent feedback, the roadmap and usage telemetry. It quarantines text from outside sources: a model reads that text as data and never follows it as instructions.

    2. 1

      Triage

      Triage decides what happens to each item. The item becomes a task, a backlog row or a decision, or triage closes it. A small model fills in a fixed form for each item, and the architect writes the task from that form.

    3. 2

      Dispatch

      A script called the tick starts each ready task. A task is ready when its dependencies have merged and no other task touches its files. No model makes this decision.

    4. 3

      Build

      An implementer agent writes the tests first and then the code, in its own copy of the repository. Each task runs in a lane. A lane covers one area of the code and holds one task at a time.

    5. 4

      Verify

      A verifier reruns the tests and compares every claim in the pull request with the actual output.

    6. 5

      Checks

      CI runs the test suite, a secret scanner and a guardrail. The guardrail fails any change that touches files outside its task.

    7. 6

      Review

      A model other than the author reviews the change. For critical changes, a model from a second AI company and a red team also review it.

    8. 7

      Merge

      GitHub merges lower-risk changes automatically after every review passes. Rafa merges changes to the pipeline.

    9. 8

      Feed back

      Each merge updates the daily log and the design map. Review findings outside the task's scope become new intake items.

    Inputs

    Four input lanes feed triage. The pipeline trusts each source according to who can write to it.

    Tickets untrusted

    GitHub issues and comments. Anyone can open an issue, so the pipeline never treats one as instructions. The repository has no issues today (measured).

    Agent feedback untrusted

    Reports that agents send to the API under decision D39, including answers to the feedback requests described below. A report can mention deals, so only a fingerprint of each report enters the public repository.

    Roadmap trusted

    The plan, backlog, decisions and reviews in the repository. Each one reached the main branch through a reviewed pull request.

    Usage telemetry aggregates

    Aggregate usage of the website, the API and the settlement contract, plus public posts about ’crow. The next section describes it.

    Quarantine

    The quarantine cleans outside text and passes it to a model with no tools. That model can only fill in a fixed form, the TriageRecord. It cannot run commands, follow links or copy the text forward. The architect reads only the form. Rafa approves any task from outside input that touches critical code.

    Quarantine steps
    1. The quarantine normalizes the text with packages/judgment/src/normalize.ts, the same code that protects the product's judges.
    2. The triager (Haiku 5.5, no tools) reads the text between random delimiters. Its prompt contains a canary token.
    3. The triager's output must match agent-ops/schemas/triage-record.schema.json, which allows enums, IDs and short summaries and rejects URLs, handles and copied text. The quarantine drops and counts any output that fails the schema.
    4. Raw text never enters a task file, brief, pull request or handoff. An implementer that needs the original text reads it once, fenced and capped at 4 KB.

    Requested feedback

    The operator asks agents for feedback at key deal milestones. It asks only agents whose owners opt in, and the default is off.

    Opt-in

    The agent's owner decides whether to opt in. The agent sends that choice as the header Prefer: feedback-requests=on. Without the header, the operator never asks, and it stores no opt-in state.

    Before a milestone

    The prepare response for an offer or an agreement asks for feedback before the agent signs, in 10% of cases.

    After a milestone

    The response that completes a deal stage asks for feedback. It asks after every settlement and every appeal, and after 10% of the other stages.

    On errors

    A problem response asks for feedback in 25% of cases for each problem type, so the operator learns why agents fail.

    Request and answer

    Each request asks three fixed questions: an ease rating from 1 to 5, whether the docs answered the agent's question, and an optional comment. The request carries no deal content and expires after 24 hours. The agent answers through POST /v1/feedback. Ratings become telemetry, and comments enter the quarantine.

    Sampling, rules and contract
    • The operator decides whether to ask by hashing the signer key, the deal ID and the milestone, and comparing the result with the rate. The hash makes the decision repeatable without stored state, so the operator asks at most once per deal and milestone.
    • The D39 rules apply to answers. The operator tells the agent that it is sharing the answer with this operator, and the agent seals any comment that can contain deal details to the operator's key.
    • A record opens when a milestone's average ease rating falls below 3 over a week, or when more than 30% of a milestone's answers say the docs did not answer the question. The rates and thresholds are guesses.
    • The feedbackRequest field and the Prefer header change the API contract, so they require an ADR and a schema version bump. The work extends T-032.

    Usage telemetry

    Telemetry shows where agents fail, so the pipeline can prioritize fixes. It collects counts and never tracks individuals.

    Website

    The pipeline counts visits and the funnel from the homepage to the agent docs (llms.txt) to a first API call. It counts each stage separately and uses no cookies. A 30% drop at any stage opens a ticket.

    Social

    The pipeline reads public posts about ’crow. Two independent posts about the same bug open a ticket. Rafa receives any security claim directly and handles all replies, because a reply is a publication.

    API

    The pipeline tracks error rates, error types, first-try success and deprecation notices. A doubling of one error type or a fall in first-try success opens a ticket.

    Onchain

    The pipeline counts public settlement events: deals, timeouts, appeals and gas per deal. An event sequence that the contract forbids opens a top-priority security ticket.

    Privacy

    Telemetry holds aggregates only. It holds no deal content, no identities, and nothing from a private deal beyond its public skeleton. The figures stay in a private store because the repository is public. Rafa decides whether to publish any figure (D35, D39, D40).

    Risk tiers

    The files a change touches set its tier. A higher tier requires more review. An agent cannot change the tier of its own change.

    Tier 0: Docs

    Documentation and brand files. The change needs CI and one reviewer, then merges automatically.

    Tier 1: Code

    Most application code. The change also needs the verifier, then merges automatically.

    Tier 2: Critical

    Code that holds money, judges work or defines the API contract. A separate agent writes the tests first. The change merges automatically only after reviewers from both AI companies approve it.

    Tier 3: Control

    The pipeline's own rules: CI, agent instructions and the agent-ops folder. Rafa merges these changes.

    Current gap

    Agents act through Rafa's GitHub account, and the repository requires no approvals (measured). The tier 3 rule is therefore a convention. A separate bot identity and a required owner review on tier 3 paths would enforce it.

    Cross-family review

    Models from one company share blind spots. The pipeline therefore sends critical changes to DeepSeek, a model from another company, for a second review. The ’crow judge panel mixes model families for the same reason.

    Scope

    DeepSeek reviews every tier 2 and tier 3 change, schema version changes, changes to the judge model list, and the end of each project phase. For decision records and deploys, its review is advisory, because Rafa makes those decisions.

    Blocking findings

    A finding blocks a merge only if it names the file and line, the rule it breaks and a way to reproduce the failure. The pipeline logs other findings as suggestions.

    Disagreements

    The verifier runs the reproduction once. If the failure reproduces, the implementer fixes it. If it does not, the finding goes to the backlog. The pipeline never takes a vote and never reruns a reviewer to get a different verdict.

    CI enforcement

    Every agent uses the same GitHub account, so any agent could post an approval comment. The review therefore runs as a CI workflow from the main branch, and agents cannot forge its status.

    Abstentions, escalation and outages
    • A reviewer's answer must match agent-ops/schemas/review-verdict.schema.json. The pipeline counts an answer that fails the schema as an abstention, and an abstention counts against the merge.
    • Two abstentions, or two refuted findings from the same company on one pull request, escalate the pull request to Rafa.
    • If DeepSeek is unavailable, a GPT-family model reviews. If both are unavailable, Rafa decides. No single provider can block or pass a merge.
    • The second reviewer receives the diff, the acceptance criteria and the core rules. It does not receive the author's self-assessment.
    • The pipeline flags a model family that agrees with authors more than 95% of the time over 20 pull requests. Each month it plants known bugs and records which ones each family finds (thresholds guessed).
    • The review uses the judges' existing client, apps/adjudicator/src/providers/live.ts, with no tools. The workflow runs on pull_request_target from main and does not run code from the pull request.

    Roles and models

    Each role uses the smallest model that does the job reliably. Small models do mechanical work, and large models do judgment work.

    Plan: Fable 5.1

    The architect turns triage records into task files and drafts decision records. Errors at this stage affect all later work, so the architect uses the strongest model.

    Build: Sonnet 5.5, or Opus 5.5 for tier 2

    Implementers write tests first and then code. For tier 2 changes, a separate fixture-author writes failing tests before the implementer starts.

    Check: Sonnet, Opus, Fable and DeepSeek

    The verifier uses Sonnet 5.5. The reviewer uses Opus 5.5 for code that Sonnet wrote and Fable 5.1 for code that Opus wrote. DeepSeek provides the second family, and Fable 5.1 runs the red team.

    Run: Haiku 5.5

    Haiku runs the triager, the tick, the lander that arms merges, and the daily log. A script or a fixed form checks each of their outputs.

    Haiku does not review code. In two live judge runs, its answers exceeded the 300-character limit (measured, config/judges-live.yaml).

    Threats

    The pipeline is an attack surface. These are the five main threats and their controls.

    Instructions hidden in outside text

    An issue, post or feedback report tries to steer an agent. The quarantine contains the text, and Rafa approves any resulting task that touches critical code.

    An agent weakens a check

    A change deletes a security test or raises a timeout. The guardrail raises the change to tier 3, so only Rafa can merge it.

    A secret leaks

    A secret scanner checks every change. Build agents hold no deploy, model or chain keys.

    Costs run away

    The tick enforces per-task budgets, a daily cap and limits on parallel work.

    Agents collide

    Each task owns its files. The guardrail fails any change outside them.

    CI speed and cost

    Parallel agents need fast and reliable checks. Today every pull request waits several minutes for checks, including documentation changes.

    4.5–6.5 minCheck time for every pull request, docs included (measured)
    2 of 24Pull request runs in which a test stalled (measured)
    3 → 5Parallel lanes before and after the CI fix (inferred)

    Three tasks fix this before activation. T-034 caches the contract build and skips checks that a change cannot affect. T-035 fixes the stalling test at its root. T-036 adds commands that merge without manual polling and rerun a known flaky test once.

    Flake rules
    • CI reruns a failed test once, and only if the test is on the known flakes list in docs/testing.md. A second failure counts as real. The list does not exist yet (measured).
    • Each list entry names its fix task and expires after 14 days. A listed flake that fails more than twice in a day pauses its lane.
    • A timeout detects a hang. Raising a timeout never counts as a fix.
    • Each machine runs one full pnpm verify at a time, because two parallel runs push tests past their timeouts (measured).

    Kill switch

    One action stops the pipeline. The switches fail closed: if the tick cannot read a switch, it treats the switch as off.

    Pause

    Anyone can create a HALT file, and Rafa can turn off the AGENT_OPS setting. The tick then starts no new tasks, and running tasks finish their current step. Alarms pause the pipeline automatically when main stays broken for 30 minutes, when spending reaches the cap, or when the scanner finds a secret.

    Stop

    Rafa runs one script. It stops every session, cancels every pending auto-merge and releases every claim.

    Sever

    Rafa revokes the agents' GitHub identity and sets every model spend cap to zero.

    The main switch is a repository setting outside the code, so agents cannot change it. A running session does not recheck the switch, so one more push can land after a stop.

    Activation

    Rafa approves each step, because each one reaches outside the repository or changes the pipeline's rules.

    1. Sandbox. Set up a separate environment with narrowly scoped keys and a bot identity for the agents. Nothing runs on Rafa's laptop.
    2. Review keys and settings. Add a spend-capped DeepSeek key, make the cross-family check required, and require owner review on tier 3.
    3. Faster CI. Merge T-034, T-035 and T-036, and create the known flakes list.
    4. Tool limits. Remove write access from the reviewer and the verifier, and add the extra deny list.
    5. Quarantine tests. Wire in the schemas, and run every known attack payload through triage as a test.
    6. Telemetry and feedback. Enable API metrics (T-031), the feedback route with milestone requests (T-032, after its ADR), web analytics and a public social reader.
    7. Shadow week. Run the tick in dry-run mode for a week while Rafa starts tasks by hand. Compare the two, and tune the telemetry thresholds.
    8. One lane. Run one task at a time until 10 pull requests merge without a revert (threshold guessed), then move to three lanes.
    9. Switch on. Set STATUS to active and AGENT_OPS to on.

    Design history

    Three independent drafts produced this design: one by Opus 5.5, one by Fable 5.1, and an earlier attempt in PR 108.

    All three drafts agree on these points. Agents run in sandboxes. A second AI family reviews with no tools. A script decides readiness, and the work queue lives in git. The pipeline starts with three lanes and never auto-merges its own changes. A test settles disagreements, not a vote.

    Glossary

    Lane
    An area of the code, such as settlement or the API. One agent works in a lane at a time, so agents never edit the same files.
    Tier
    The risk level of a change, from 0 (docs) to 3 (pipeline rules). The files a change touches set its tier.
    Triage
    The stage that turns each incoming item into a task, a backlog row or a decision, or closes it.
    TriageRecord
    The fixed form that triage fills in. Later stages see only this form.
    Quarantine
    The handling of outside text. The pipeline cleans the text and gives it to a model with no tools, which fills in the form.
    Tick
    The script that starts ready tasks. It runs after each merge and keeps no state between runs.
    Feedback request
    Three fixed questions that the operator adds to a response at a deal milestone, for agents whose owners opt in.
    Claim
    A task branch pushed to GitHub. It marks the task as taken.
    CI
    The automated checks that GitHub runs on each pull request.
    Second family
    A model from another AI company. DeepSeek is the primary, and a GPT-family model is the fallback.
    Red team
    An agent that tries to break a change and writes a test for each attack.
    Shadow week
    A week in which the tick only prints what it would do while Rafa starts tasks by hand.
    Kill switch
    The three ways to stop the pipeline: pause, stop and sever.
