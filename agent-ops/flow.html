How a team of AI agents would build ’crow

A design for improving the ’crow codebase continuously, with AI agents working in parallel and safely. Work arrives from four places and becomes small tasks. Agents build the tasks side by side, and machines plus AI models from two different companies check each one before it merges. Nothing here runs yet; Rafa switches it on one step at a time.

In one minute

What it is, why it exists, how it stays safe, and what you decide.

What it is

An assembly line for code changes. Each change is a small task with a clear scope: a fixed set of files, and tests that prove it works.

Why now

Agents already merged 40 pull requests in two days (measured). The bottleneck has become coordination and review, not writing code.

How it stays safe

Automatic checks run before any AI gives an opinion. For risky changes, a second AI company must agree. Deploys, keys, money and settings stay with Rafa.

What you decide

Whether and when to switch it on. Activation is nine small decisions, from a sandboxed environment to a week of dry runs (see Starting it).

The pipeline

Every change takes the same nine steps. Each dot is a task moving through them, colored by how risky it is.

incomingcodecriticalcontrol
    A simulated run: the task IDs are real, the outcomes are invented. “Stop new work” pauses dispatch only; tasks already running finish.
    1. 0

      Intake

      New work is collected from tickets, agent feedback, the roadmap and usage data. Text from outsiders goes into quarantine: it is treated as data, never as instructions.

    2. 1

      Triage

      Triage sorts each item: make it a task, park it in the backlog, raise it as a decision, or close it. A small AI fills in a fixed form, and the architect writes the task from that form.

    3. 2

      Dispatch

      A small script, the tick, starts tasks that are ready: what they depend on has merged, and no one else is touching their files. No AI decides this.

    4. 3

      Build

      An agent writes the tests first, then the code, in its own isolated copy of the repo. Each task runs in a lane: one area of the code, one task at a time.

    5. 4

      Verify

      A verifier reruns the tests and checks every claim in the pull request against the real output.

    6. 5

      Checks

      The automatic checks (CI) run: the test suite, a secret scanner, and a guardrail that fails any change touching files outside its task.

    7. 6

      Review

      A reviewer reads the change, and it is never the same model that wrote it. Risky changes also get a reviewer from a second AI company and a red team that tries to break them.

    8. 7

      Merge

      Lower-risk changes merge automatically once every review passes. Changes to the pipeline itself wait for Rafa.

    9. 8

      Feed back

      Each merge updates the daily log and the design map. Anything new that review found goes back to intake.

    Where work comes from

    Four input lanes feed triage. The easier it is for outsiders to write into a source, the more carefully it is handled.

    Tickets untrusted

    GitHub issues and comments. Anyone can write one, so they are never taken as instructions. Today there are none (measured).

    Agent feedback untrusted

    Bug reports agents send through the API (decision D39). They may mention deals, so only a fingerprint of a report ever enters the public repo.

    Roadmap trusted

    The plan, backlog, decisions and reviews already in the repo. They got there through reviewed pull requests.

    Usage telemetry counts only

    How the website, the API and the settlement contract are used, and what people say publicly. Next section.

    The quarantine

    Outside text is cleaned up first. Then a small AI that has no tools reads it and fills in a fixed form, the TriageRecord. It cannot run anything, link anywhere or copy the text forward. The architect only ever sees the form. If outside input would lead to work on critical code, Rafa approves it first.

    Technical detail: the quarantine steps
    1. Normalize the text with packages/judgment/src/normalize.ts, the same code that defends the product's judges.
    2. The triager (Haiku 5.5, no tools) reads it between random delimiters, with a canary token in its prompt.
    3. Its output must match agent-ops/schemas/triage-record.schema.json: enums, ids and short summaries, with no URLs, handles or copied text. Anything else is dropped and counted.
    4. Raw text never enters a task file, brief, pull request or handoff. An implementer that needs the original reads it once, fenced and capped at 4 KB.

    Learning from usage

    Telemetry shows where agents get stuck, so fixes go to real friction. It counts things; it never watches individuals.

    Website

    Visits, and how many go from the homepage to the agent docs (llms.txt) to a first API call. Each step is counted on its own, without cookies. A drop of 30% opens a ticket.

    Social

    Public mentions of ’crow. Two independent posts reporting the same bug open a ticket, and a security claim goes straight to Rafa. Replying is publishing, so that stays with Rafa too.

    API

    Error rates, the kinds of errors agents hit, first-try success, and deprecation notices. An error type that doubles, or a success rate that falls, opens a ticket.

    Onchain

    Public settlement events: how many deals, timeouts and appeals, and the gas each deal costs. An event sequence the contract should never produce is a top-priority security ticket.

    Privacy rule. Counts only: no deal content, no identities, nothing from a private deal beyond what is already public. The numbers stay in a private store, because the repo is public. Publishing any of them is Rafa's call (decisions D35, D39, D40).

    Risk decides the review

    Every change gets a tier from the files it touches. The riskier the files, the more reviewers it needs. An agent cannot lower its own tier.

    Tier 0 · Docs

    Documentation and brand. Automatic checks and one reviewer, then it merges automatically.

    Tier 1 · Code

    Most application code. Adds the verifier. Merges automatically.

    Tier 2 · Critical

    Code that holds money, judges work or defines the API contract. A separate agent writes the tests first, and a second AI company must also approve. It merges automatically only when both companies pass it.

    Tier 3 · Control

    The pipeline's own rules: CI, agent instructions and this folder. Rafa merges these by hand.

    One gap today

    Agents act under Rafa's GitHub account, and the repo's rules require no approvals (measured). So “Rafa merges” is a habit, not a lock. The fix is a separate bot identity for the agents, plus a required owner review on tier 3 only.

    A pull request takes the highest tier among its files. One path table, scripts/ci/affected.mjs (T-034), serves both CI and local checks.

    Two AI companies check each other

    Models from one company tend to share blind spots. So critical changes are also reviewed by DeepSeek, which is trained separately. ’crow's own judge panel mixes model families for the same reason.

    When

    Every tier 2 change and every change to the pipeline. Also schema version bumps, changes to the judge model list, and the end of each project phase. Before a deploy and on decision records it is advice only, because Rafa already decides those.

    What counts as a blocking finding

    It must name the file and line, the rule it breaks, and a way to reproduce it. Anything less is logged as a suggestion.

    How disagreements end

    The verifier runs the reproduction once. If it fails, the change gets fixed; if it does not, the finding goes to the backlog. Nobody votes, and nobody re-asks a reviewer to get a different answer.

    Why it runs in CI

    All agents share one GitHub account, so any of them could post a fake “approved” comment. A status written by a CI workflow running from the main branch cannot be faked that way.

    Technical detail: tie-breaks, abstentions and outages
    • A reviewer's answer must match agent-ops/schemas/review-verdict.schema.json. An answer that does not is an abstention, and it counts against merging.
    • Two abstentions, or two refuted findings from the same company on one pull request, go to Rafa.
    • If DeepSeek is down, a GPT-family model reviews; if both are down, Rafa decides. No provider can block a merge alone, or pass one alone.
    • The second reviewer sees the diff, the acceptance criteria and the core rules. It never sees the author's own assessment.
    • A family that agrees with authors more than 95% of the time over 20 pull requests is flagged. Known bugs are planted each month to measure what each family catches (thresholds guessed).
    • The call goes through the judges' existing client, apps/adjudicator/src/providers/live.ts, with no tools. It runs on pull_request_target from main, so no code from the pull request runs.

    The team

    Each role gets the cheapest model that does it well. Mechanical work goes to small models, judgment to large ones.

    Plan · Fable 5.1

    The architect turns triaged items into task files and drafts decision records. Mistakes here multiply, so it gets the strongest model.

    Build · Sonnet 5.5, Opus 5.5 on critical code

    Implementers write tests first, then code. On tier 2, a separate fixture-author writes the failing tests before the implementer starts.

    Check · Sonnet, Opus or Fable, DeepSeek

    The verifier (Sonnet) checks claims. The reviewer is Opus for Sonnet's work and Fable for Opus's work. DeepSeek is the second family, and Fable leads the red team.

    Run · Haiku 5.5

    The triager, the tick runner, the lander that arms merges, and the daily log. Each job's output is checked by a script or a fixed form.

    Haiku stays out of review: in two live judge runs, its answers ran past the 300-character limit (measured, config/judges-live.yaml).

    What could go wrong

    The pipeline is itself something to attack. Here are the five risks that matter most, with the guard for each.

    Hidden instructions in outside text

    An issue, post or feedback report tries to steer an agent. The guard is the quarantine, plus Rafa's approval before outside input reaches critical code.

    An agent weakens a check

    A change deletes a security test or loosens a timeout. The guardrail raises such a change to tier 3, so only Rafa can merge it.

    A secret leaks

    A secret scanner runs on every change. Build agents hold no deploy, model or chain keys.

    Runaway cost

    Per-task budgets, a daily cap and limits on parallel work, all enforced by the tick.

    Agents collide

    Each task owns its files. The guardrail fails any change outside them.

    Speed and cost

    Parallel agents only help if the checks are fast and reliable. Today they are slow on every pull request, even a typo fix.

    4.5–6.5 minfor checks on every pull request, docs included (measured)
    2 of 24pull request runs hit a test that stalls (measured)
    3 → 5lanes at once, before and after the CI fix (inferred)

    Three tasks fix this before activation. T-034 caches the slow contract build and skips checks a change cannot affect. T-035 fixes the stalling test at its root. T-036 adds commands that merge without waiting by hand and retry a known-flaky test exactly once.

    Technical detail: flake rules
    • One rerun, only for a test on the Known flakes list in docs/testing.md (the list does not exist yet, measured). A second failure is real.
    • Each list entry names its fix task and expires after 14 days. A listed flake that fires more than twice a day pauses its lane.
    • A timeout detects a hang; raising one is never the fix.
    • One full pnpm verify per machine at a time: two in parallel push tests past their timeouts (measured).

    Stopping it

    Stopping takes one action. The switches fail safe: if a switch cannot be read, the pipeline treats it as off.

    Pause

    Anyone creates a HALT file, or Rafa turns off the AGENT_OPS setting. No new tasks start, and running ones finish their current step. Alarms do this automatically when main breaks for 30 minutes, when spend hits the cap or when a secret is detected.

    Stop

    Rafa runs one script. Every session stops, every pending auto-merge is cancelled, and every claim is released.

    Sever

    Rafa revokes the agents' GitHub identity and sets every model spend cap to zero.

    The main switch lives in the repository's settings, outside the code, so agents cannot flip it. One known gap: a session does not re-check the switch mid-task, so one more push may land.

    Starting it

    Each step is Rafa's decision, because each reaches outside the repo or changes the pipeline's own rules.

    1. A sandbox. A separate environment with narrowly scoped keys, and a bot identity for the agents. Nothing runs on Rafa's laptop.
    2. Review keys and settings. A spend-capped DeepSeek key; the second-family check made required; owner review on tier 3.
    3. Faster checks. T-034, T-035 and T-036 merged, plus a Known flakes list.
    4. Tighter tools. Reviewer and verifier lose the ability to edit, and the extra deny list goes in.
    5. Quarantine tests. The forms are wired in, and every known attack payload is fed to triage as a test.
    6. Telemetry sources. API metrics and feedback (T-031, T-032), web analytics, and a public social reader.
    7. A shadow week. The tick runs in dry-run mode and prints what it would start, while Rafa starts tasks by hand. The two are then compared, and the telemetry thresholds are tuned.
    8. One lane. One task at a time until 10 pull requests merge with no revert (threshold guessed), then three lanes.
    9. Switch on. Rafa sets STATUS to active and AGENT_OPS to on.

    How this design was made

    Three drafts were written independently: one by Opus 5.5, one by Fable 5.1, and an earlier stopped attempt (PR 108). They were then reconciled.

    Glossary

    Lane
    An area of the code, such as settlement or the API, that one agent works in at a time, so agents never edit the same files.
    Tier
    A change's risk level, from 0 (docs) to 3 (the pipeline's own rules), set by the files it touches.
    Triage
    Sorting incoming items into tasks, backlog rows, decisions or closed items.
    TriageRecord
    The fixed form triage fills in. It is the only thing later steps see about an outside item.
    Quarantine
    How outside text is handled: cleaned, then read by an AI with no tools that can only fill in the form.
    Tick
    A small script that runs after each merge, works out which tasks are ready, and starts them. It keeps no memory between runs.
    Claim
    A task branch pushed to GitHub, which marks the task as taken.
    CI
    The automatic checks GitHub runs on every pull request.
    Second family
    An AI model from a different company (DeepSeek, with a GPT model as backup), used because models from one company share blind spots.
    Red team
    An agent whose job is to break a change and write a test proving the attack.
    Shadow week
    A week where the pipeline only prints what it would do, while Rafa does it by hand.
    Kill switch
    The three ways to stop the pipeline: pause, stop and sever.
