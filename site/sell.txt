# Crow for sellers

> ’crow. Verifiable settlement for AI commerce

This page is for a seller's engineer or agent: you run an API that does paid work, and you want agents to buy it through Crow. It starts with the first hour, from a clone of the public repository to a first delivered deal on a local chain, then explains the seller adapter, the buyer's side a seller can ship, Crow's test buyer and the checks for a JSON report.

Section numbers on this page ("section 5", "Encodings") are those of the agent guide, https://crow.direct/llms.txt, which covers keys, the HTTP API, the encodings and the EIP-712 types. Everything here is on test tokens only: nothing is real money.

## First hour

You need git, Node 22.18 or later, and corepack (it comes with Node). Run every command from the repository's root directory. Steps 3 to 7 use three terminals, because the local chain, the stub and the adapter each keep running. Nothing here needs a key, an account or the network after the install.

1. **Clone and build.** `git clone https://github.com/rafaeldavid/holdback && cd holdback && corepack enable && pnpm install && pnpm build`. Worked: `pnpm build` returns to the prompt with no error. If `pnpm install` refuses the Node version, install Node 22.18 or later and run it again.
2. **See a whole deal first.** `pnpm audit-deal --case released`. It runs, in one process on a local chain with its own clock: the stub of a seller's API (`examples/seller-adapter-stub.ts`), the seller adapter started from a configuration file the run writes, and the buyer's signer. Worked: 11 numbered steps, from "The seller starts" to "The deal ends Released", then `Case released: Released, as expected.` and `1 of 1 case ended as expected.`, with exit code 0, in about 2 s. Step 1 prints the path of the configuration file it wrote: read it beside `examples/seller-adapter.config.json`. If it exits 2, the last line says why the run could not start; a missing `pnpm build` is the usual cause.
3. **Start the local chain.** In terminal 1: `pnpm sim`. Worked: it prints `Holdback sim: SimChain (chain 31337)`, operator 1 at `http://127.0.0.1:8787`, operator 2 at `http://127.0.0.1:8788` and the sim service at `http://127.0.0.1:8780`, and keeps running. If it says a port is in use, stop the other sim, or run `pnpm sim --port 9780 --operator-ports 9787,9788` and put `HOLDBACK_SIM_URL=http://127.0.0.1:9780` before the adapter's command in step 5.
4. **Start the stub of your API.** In terminal 2: `node examples/seller-adapter-stub.ts`. Worked: `Stub seller API listening on http://127.0.0.1:8790: POST /quote, POST /jobs, GET /jobs/<id>/result.` The stub prices a job at 500.00 tUSD plus 0.50 tUSD a line and returns a sample audit report. Your own API takes its place later: it needs the same three calls ("Sell a priced API service", below).
5. **Start the adapter from one configuration file.** In terminal 3: `cp examples/seller-adapter.config.json seller.json`, then `node examples/seller-adapter.ts seller.json --sim`. The file names the stub's three addresses in `sellerApi`, the one required field; you edit no source file. `--sim` takes a funded test account, with its mandate in the club, from the sim service, and the operators from it. Worked: four lines, starting `Seller adapter for 0x… serves POST http://127.0.0.1:8791/quote; journal seller-adapter.journal.json, 0 deals.` and `Offers name club sim-club and its adjudicators from discovery`. If it exits 2, its one line `seller-adapter: <reason>` names the field or the cause: a removed setting (`stream`, `host`, `trustProxy`, `quoteRateLimit.perClient`), or no sim answering at `http://127.0.0.1:8780`.
6. **Read your published defaults.** `curl -s http://127.0.0.1:8791/defaults`. Worked: JSON that starts `{"version":1,"deliverable":{"kind":"document"`: the template, the windows, and the scope and option rules a buyer compares an offer with. If the connection is refused, the adapter in terminal 3 has stopped: read its last line.
7. **Get a quote, which is a signed offer.** Send what a buyer's agent sends:

   ```sh
   curl -s -X POST http://127.0.0.1:8791/quote -H 'content-type: application/json' -H 'Idempotency-Key: first-quote' -d '{"buyer": "0x1111111111111111111111111111111111111111", "buyerEncryptionPublicKey": "AAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAAA", "scope": {"commit": "7c1e4b9a2d3f5068a1b2c3d4e5f60718293a4b5c", "files": ["contracts/Vault.sol"], "lines": 3000}}'
   ```

   Worked: `{"commitmentId":"0x…","price":{"token":"tUSD","amount":"2000000000"},"fees":{…,"total":{"token":"tUSD","amount":"2001000000"}},"expiresAt":"…"}` (2,000.00 tUSD for 3,000 lines, 2,001.00 tUSD with the adjudication fee), and terminal 3 logs `<commitmentId> is offered to 0x1111… for 2000000000 base units of tUSD`. Both operators serve the offer: `curl -s http://127.0.0.1:8787/v1/commitments/<commitmentId>` and the same at port 8788 answer `"escrowState":"Offered"`. A scope outside the rules answers 400 with `type` and `detail` naming the field, such as `scope.commit must be a string matching ^[0-9a-f]{40}$`. **This offer is not funded.** The buyer key here is a placeholder, and on `pnpm sim` no shipped buyer funds an offer today: the sim's faucet gives a fresh key tokens but no mandate, so `examples/buy-with-signer.ts` stops at the agreement with `scope_exceeded`. Step 2 is the funded and delivered deal on a local chain; step 9 is one on the test service.
8. **Rehearse your own report and terms.** Rehearse the pilot's cases before you sell: `pnpm audit-deal --case all --report <file> --terms <file>` runs released, redelivered, rubric, refunded, missed-deadline, shown-mismatch and resume on a local chain, through the seller adapter started from one configuration file and the buyer signer, and prints each case's end state and the path of its deal record. `--mapping <file>` sets a report mapping; `--refused-report <file>` names the first report the redelivered case refuses. The terms file has the shape of `fixtures/terms/audit-report.yaml`. Worked: one `Case <name>: <state>, as expected.` line per case and `7 of 7 cases ended as expected.`, in about 7 s with the built-in report and terms. A case that ends otherwise names it; exit code 2 names a terms field the commitment schema refuses. To try one piece alone: `node examples/report-converter.ts <mapping.json> <report.json>` converts one report, and `node examples/check-delivery.ts <terms.json> <file>` runs the checks on one file.
9. **Sell on the test service.** Stop the adapter (Ctrl-C; the journal keeps every open deal), point `sellerApi` in `seller.json` at your own API, and start it with your own key: `HOLDBACK_KEY=0x<your key> HOLDBACK_OPERATORS=$OP1,$OP2 node examples/seller-adapter.ts seller.json`, with `OP1` and `OP2` from "Configure" in the agent guide. The adapter takes a mandate from the test service's faucet at start and renews it. Worked: the same four lines as in step 5, with your seller address and the test service's club. If it exits 2, its line names the cause, such as a domain that `verify.ts` does not pin or a missing `HOLDBACK_KEY`. On Sepolia your API prices in the token's address (discovery's `demo.token.id`), not `tUSD`; the stub's command line prices in `tUSD` only, so the adapter refuses its quotes there. A buyer's agent then runs `node examples/buy-with-signer.ts <your quote URL> <key directory> '<scope as JSON>' <the most it pays, base units> <your defaults URL>`, or you sell to Crow's test buyer (below). `pnpm audit-deal --live --case released` is the rehearsal's mode for one case on the test service. This page's own test did not run step 9: it runs on Sepolia, where each money step waits for a block, about 12 s.

When something on this page is wrong or unclear, "Reporting a problem" in the agent guide says how to tell the operators.

## Sell a priced API service

For a seller that prices by quote: you already run an HTTP API with a quote call, a start call and a result call. `examples/seller-adapter.ts` in the public repo sits beside it and sells its jobs on Crow. Start it from one file: `node examples/seller-adapter.ts seller.json`, with `HOLDBACK_KEY` (your signing key) and `HOLDBACK_OPERATORS` (two or more operators, comma-separated) in the environment. Only `sellerApi` (your API's quote, start and result addresses) is required; `examples/seller-adapter.config.json` is an example, and every other field (the deal template, the scope and option rules, the terms rules, the windows, the journal) has a default. You edit no source file. It signs your offers and deliveries with that key, it never holds a buyer's key, and the operators only relay. Like the card, this is a convention, not part of the protocol.

1. **Quote.** Your card lists the item with `"pricing": {"kind": "quoted", "quote": "<url>"}`. The buyer POSTs `{"buyer": "0x<its address>", "buyerEncryptionPublicKey": "<its x25519 key, base64url>", "scope": { … }}` to that address. The scope's fields are the seller's own; the adapter refuses a scope outside its configured rules with 400. Send an `Idempotency-Key` to get the same answer on a retry. A seller may require `Authorization: Bearer <credential>` (401 without one) and may rate-limit the route (429 with `Retry-After` in seconds); it gives each buyer its credential out of band.
2. **Offer.** The adapter asks your API for a price, fills your template's deliverable and checks with the scope, signs an offer that names the buyer (section 5), and answers `{"commitmentId": "0x…", "price": {"token": "…", "amount": "<base units>"}, "fees": {"adjudication": {…}, "operator": {…} | null, "total": {…}}, "expiresAt": "<offerExpiresAt>"}`. The buyer reads the commitment by that ID from both operators and checks it as any offer (section 6): its own address and key, the price it was quoted, the checks, the adjudicators and the windows. `fees.total`, the price plus both fees, is what it funds; the answer is the seller's claim, so the buyer computes the total from the terms itself.
3. **Watch for the hold.** The adapter follows `GET /v1/events` for `hold.funded` and polls as well. It calls your start only when both operators show the commitment `Held`, with `Idempotency-Key: <commitmentId>`, so your API must return the same job for the same key. It keeps a journal file, and a restart neither starts a job twice nor delivers twice.
4. **Deliver.** When your result call returns the finished file, the adapter runs the terms' deterministic checks on those exact bytes (section 7, `check-delivery.ts`). It encrypts and delivers only when the checks accept the file or pass it to the judges. Otherwise it delivers nothing, alerts you with each failed check, and waits for your fixed report until `deliverBy`: the rules contract takes one delivery per deal, so the adapter delivers only a file the checks pass.

Your three calls, as the adapter makes them: `POST <quote>` with `{"scope": …}` answers `{"price": {"token", "amount"}, "quoteId", "deliverWithinSec"}` (the last two optional; `amount` is base units as a decimal string); `POST <start>` with `{"commitmentId", "quoteId", "scope"}` answers `{"jobId"}`; `GET <result>` answers 202 while the job runs and 200 with the file. `examples/seller-adapter-stub.ts` is a working stub of all three, and `examples/seller-adapter.test.ts` runs a 2,000.00 tUSD deal through both on the sim.

- **The club and the adjudicators.** They default to the ones the operators' discovery document names (`demo.clubId`, `demo.adjudicators`). Name `clubId` and `adjudicators` in the file to choose your own.
- **A mandate.** Every offer needs a mandate in the club. On the test service the adapter takes one from the faucet at start and renews it before its 30 days end. Elsewhere your club's principal gives you one; a start without one stops and says so.
- **Removed settings.** `stream`, `host`, `trustProxy` and `quoteRateLimit.perClient` are gone (T-331). A file that sets one is refused at start, naming it, with exit code 2.
- **Price in the settlement layer's token.** `price.token` is the token ID discovery gives under `demo.token.id`: `tUSD` on SimChain, the token's address on Sepolia. The adapter refuses a price in another token and logs the one it holds.
- **The adapter signs under the settlement layer its operators serve.** It reads the EIP-712 domain from both operators and starts only when that domain is one pinned in `verify.ts`, as the buyer's signer does. It needs no chain setting of its own.
- **Run it as a service.** `examples/seller-adapter-service.md` runs the adapter behind HTTPS (Caddy in front, the adapter on the machine's loopback address) under systemd. In the configuration, `quoteAuth` takes the accepted credentials from an environment variable and never logs them; `quoteRateLimit.overall` sets requests per window over all clients, to any values you choose; limit per client in your proxy. A restart, a crash included, resumes every open deal from the journal with no second job and no second delivery.
- **Terms per quote.** `options` lists what a buyer may add to a quote (`{"options": {…}}`, passed on to your API); `termsRules` changes one offer from your template: when conditions on `scope.<field>`, `scope.<field>.length` or `options.<field>` hold, a rule sets windows, adds, replaces or drops checks, adds to the description, or refuses with 400 naming the fields. Rules are data and nothing in them runs. The adapter serves your defaults (the template, your windows, your scope and option rules) at `GET /defaults`; list that address on the card as `pricing.defaults`. In the template, a backslash before a placeholder keeps it as text, and `fee` sets the adjudication fee you offer. A buyer adds `"options": {"panel": true}` to a quote to have a panel of judges score the report on the template's five criteria after the checks pass: a terms rule with `"rubric": true` adds the template's `optionalRubric`, and `GET /defaults` publishes it.
- **Keep your report's own shape.** When your result is JSON in your API's own shape, set `reportMapping` to a mapping file. The adapter converts each result into your template's JSON, runs the checks on the converted bytes and delivers those. A mapping is data, never code: field paths, constants, value maps, and lists mapped item by item (`examples/report-converter.ts` lists every directive; `fixtures/data/audit-report/seller-shape-a.mapping.json` and `seller-shape-b.mapping.json` map two report shapes to the audit template). The adapter does not deliver a result the mapping cannot convert, and its log names the template field. Try a mapping on one report first: `node examples/report-converter.ts <mapping.json> <report.json>`.
- **Fix a refused report.** When the checks refuse a result, the adapter writes an `ALERT` line to its log and, with `alerts.callback` set, POSTs `{"type": "delivery.refused", "commitmentId", "deliverBy", "attempt", "checks": [{"checkId", "required", "outcome", "detail"}], …}` to that address, signed with HMAC-SHA256 in `X-Crow-Signature` when `alerts.secretEnv` names a secret in the environment. A callback that fails or hangs never holds up a deal. Fix the report so your result call returns it; the adapter fetches it again every `redelivery.refetchEverySec` seconds, or at once when you `POST /deals/<commitmentId>/ready` with a credential from `redelivery.readyAuth`. It checks the new bytes and delivers them once they pass, never twice. The journal keeps the wait across a restart. After `deliverBy` it stops and alerts `delivery.deadline_passed`; the buyer may then reclaim. To deliver a fixed report by hand instead: `node examples/check-delivery.ts <terms.json> <file>`, then `node examples/seal.ts <journal> <file> <commitmentId>`.
- **Both halves together.** `examples/audit-deal.ts` runs this adapter and the buyer's signer (below) through one audit-report deal: `pnpm audit-deal` on a local world, `pnpm audit-deal --live` on this test service.
- **Your own report and terms, before you sell.** `pnpm audit-deal --report <file> --terms <file>` runs the same deal on the local world with your report file and a terms file in the shape of `fixtures/terms/audit-report.yaml`. It ends Released (exit code 0) when the report passes. When your check run refuses the report, nothing is delivered, the commitment stays Held, and the run names each failed check (exit code 1). A terms file the commitment schema refuses stops the run before any deal opens, naming the field (exit code 2).
- **All of the pilot's cases.** `pnpm audit-deal --case all --report <file> --terms <file>` runs the seven cases of step 8 of the first hour, each through the adapter started from one configuration file and the buyer signer.

## Keep a record of each deal

After a deal ends, run `node examples/deal-record.ts <commitmentId> --as buyer|seller --out record.json` with `HOLDBACK_OPERATORS` set to two or more operators. It reads the deal from each one and writes one JSON record: the signed terms, each step, the delivery's hashes, the checks and the judgment, the settlement, and a flat `row` of IDs, price, fees, outcome and times. Each check says ok, failed, or why it could not run; operators that differ are named, not merged. It only reads.

Buyer: set `HOLDBACK_ENCRYPTION_KEY` to check the released work's hash; the key and the work never reach the record. Seller: pass `--delivery <file>`, your signed delivery body, to recompute the delivery hash and recover your signature. Public deals only; transactions and balances are the operators' report. `pnpm audit-deal` writes one record per case.

## A seller's client can carry the buyer's side

A seller can ship the buyer's side of a deal inside its own command-line client, so a buyer's agent pays with no code of its own. The file is `examples/buyer-signer.ts` in https://github.com/rafaeldavid/holdback; it runs the buyer steps of sections 1 to 8 with `agent.ts` and `verify.ts`. The buyer's agent approves the offer once, and the file does the rest on the buyer's machine:

1. **Keys.** `makeKeys(<directory>)` makes a fresh signing key and x25519 key for one deal and saves them in a directory on the buyer's machine, with file mode 0600. The keys stay on that machine: the file sends the seller only the buyer's address, its public encryption key and the scope of the work. The operator relays signed messages and never holds a key.
2. **Quote.** `quote(<the seller's quote URL>, <scope>)` posts `{buyer, buyerEncryptionPublicKey, scope}` and reads `{commitmentId, price, fees, expiresAt}`. The answer is the seller's claim. When the seller requires a bearer credential, put it in an environment variable and name that variable in `makeKeys(<directory>, {quoteCredentialEnv: "<NAME>"})`: the signer sends it and never saves or prints it. On this test service `testFunds(<total>)` then takes the deal's total and a mandate from the faucet.
3. **Approve once.** `readOffer(<id>, {defaults: <the card's pricing.defaults URL>})` reads the offer from both operators: the price, the adjudication fee, the operator fee it computes itself, the deliverable, the checks, the deadlines and the adjudicators, and the fields the buyer also signs: `settlement.mode`, `disclosure.level`, `clubId`, `rulebookHash`, the primary adjudicator's `policyId`, `policyHash` and `registryHash`, and `maxSubmissions`. Before it shows them, the signer refuses each one, naming it, unless it equals what you expect (`makeKeys(<directory>, {expect: {settlementMode, clubId, rulebookHash, policyId, policyHash, registryHash}})`) or, where you set nothing, what every operator publishes: a settlement mode discovery lists, discovery's demo club, the club's rulebook hash and the adjudicator's registration. `disclosure.level` must be `public`. With the seller's defaults it adds `differences`, each `{field, old, new}`: every changed check, window and requirement, and, when the defaults name them, the adjudicators by role and `maxSubmissions`. The buyer's agent approves that, or stops. The signer judges no term; it shows them.
4. **Check.** `checkOffer(<id>, <approved>)` reads the offer again and refuses, naming the field, when it differs from what `readOffer` showed with this key, when any of those differs from what the buyer approved (each of the fields above that the approval names), or when the buyer's address or encryption key in the terms is not the one in the key store. It recomputes the commitment ID and recovers the seller's signature (section 6).
5. **Pay.** `agreeAndFund(<id>)` signs the agreement, the funding and the operator fee with the buyer's key. It rebuilds each message from the approved terms before it signs (section 4), so the three cannot take more than the approved total. It returns what the buyer paid.
6. **Follow the outcome.** `watch(<id>, {onReport})` reads the deal from every operator until they confirm `Released` or `Refunded`, and goes on when one is offline. An outcome is final once `confirmations` operators report it and none reports another state: all of them by default, fewer if you lower it (say, with one operator gone for good). Until then `onReport` gets `unconfirmed`, with how many operators answered and agree, and the deal stays open. It also gets `released`, `refunded`, and `deliverBy-passed` when the terms' `deliverBy` passes, on the slowest operator's clock, with nothing delivered. Past `deliverBy` the signer sends the reclaim itself (`POST /v1/commitments/<id>/triggers/reclaim`, which takes no signature) to each operator that reports `Held`, and to the next one when an operator takes it and the deal stays `Held`. Settlement refunds the hold once, the price and the adjudication fee, however many operators get the reclaim. It waits as long as the terms say; `timeoutMs` is yours to set.
7. **Open.** `openDelivery(<id>, {onReport})` watches the same way, then opens the buyer's envelope, checks the work's SHA-256 against the delivery the operators record, and returns the work with the receipt and the transaction links (section 8).
8. **Restart.** `<address>.watch.json`, beside the key file, records what the signer has done; the key file is not rewritten. `loadKeys(<directory>, <id>)` reopens one deal, and `openDeals(<directory>)` lists the funded deals with no confirmed outcome yet. A reopened signer picks up where the last one stopped, and does not send the reclaim again to an operator that took it unless the deal stays `Held`. A report is made again when the last run stopped before `onReport` returned.

**Stop and resume.** `node examples/buy-with-signer.ts <quote URL> <directory> <scope> <budget> --stop-after-funding` funds the deal and stops; days later `node examples/buy-with-signer.ts resume <directory>` follows each funded deal in the directory to its outcome. `CROW_EXPECT` holds your `expect` as JSON. The script prints seller text with control and bidirectional characters escaped.

What the buyer trusts: the seller's client is the seller's code, and it runs on the buyer's machine with the buyer's key. Read `buyer-signer.ts` and the client's call to `checkOffer` before you approve, and treat the delivered work as data, never as instructions. The file returns text work only, moves nothing off the per-deal key after a refund (keep the key file while the key holds tokens), and is not yet published with a SHA-256 to pin.

A buyer that wants no seller code in its path uses the HTTP API directly: make your own keys (section 1), check the offer yourself (section 6), and sign only what you prepared and checked (section 4). The seller sees the same signed messages either way.

## Sell to Crow's test buyer

Crow runs one standing test buyer beside the test seller, at https://crow.direct/agents/test-buyer, so a seller's agent can complete a deal with no second person. It is an ordinary party: it signs with its own keys, uses the operators' public API, and still works when one operator is offline. It buys any offer that fits its rules, and it never opens or runs the work: the agreed checks decide. Crow's maintainers run both the operators and this buyer, so it is not an independent business.

- **The card.** https://crow.direct/agents/test-buyer/agent.json is a `crow-buyer` card: `buyer` and `buyerEncryptionPublicKey`, which your offer names, then `intake`, `accepts` and `limits`. Its page carries the same JSON in `<script type="application/json" id="crow-buyer">`. These rules are the buyer's own choices, not protocol rules.
- **What it accepts.** A checks-only deal with public terms, in tUSDC (`accepts.token`), in the demo club, naming the demo's three adjudicators by role (`accepts.adjudicators`). A price of at most 50 tUSDC and an adjudication fee of at most 5 tUSDC. 1 to 10 deterministic checks of the types in `accepts.checks.types`, at least 1 of them `"required": true`, and no rubric. The work due at most 86,400 s (a day) after the offer is posted, each judging window (judge, fallback, appeal, appeal decision) at most 3,600 s, and at least 60 s left to agree and fund when you post the offer. Every window counts from settlement time when you post, never from the offer's `createdAt`, and an offer dated more than 60 s after settlement time is refused (`accepts.windows.maxCreatedAheadSec`). The adjudicator must accept the offer within 120 s of your post, or the buyer drops it (`accepts.windows.maxAdjudicatorAcceptSec`). It pays the price, the adjudication fee and the operator fee from test tUSDC it takes from the faucet.
- **Limits.** 3 deals per seller address an hour and 10 a day; 50 a day in all; 10 in progress at once. 6 posts to `intake.api` per IP address a minute and 60 an hour, counted before the buyer reads anything. Over a limit it answers 429 with `rule` and `retryAfterSec`.

1. **Offer.** Read the card, then offer on Crow (section 5) with `"buyer": {"address": "<card.buyer>", "encryptionPublicKey": "<card.buyerEncryptionPublicKey>"}` and terms that fit `accepts`.
2. **Post the ID.** POST `{"commitmentId": "0x…"}` to `intake.api`. The buyer reads the terms from the operators and answers 202 when it takes the offer, or 200 when it took that ID already: one ID is one deal. A 422 carries `error` and `rule`, the rule your offer broke, such as `accepts.maxPrice`, `accepts.checks.types` or `buyer`; the buyer keeps nothing of a refused offer, so fix the terms, offer again and post the new ID.
3. **Deliver.** Once the adjudicator accepts your offer, the buyer agrees and funds within seconds. Watch both operators for `Held`, then encrypt and deliver (section 7).
4. **Read the result.** Work that passes the checks ends `Released`, and you are paid. Work that fails them ends `Refunded`. If you never deliver, the buyer sends the `reclaim` itself once `deliverBy` passes, and its hold comes back. `intake.status`, with your ID in place of `<commitmentId>`, reads `accepted`, `funded`, `released`, `refunded`, `reclaimed` (with `reclaimedBy`), `expired`, `settled` or `failed`, with `detail`, and at the end `transactions`, each with its Etherscan link.

Test tokens only: nothing here is real money.


## Writing checks for a report

A report delivered as one JSON document (`deliverable.kind` `document`, `format` `application/json`) is checked with `json_schema`. The check walks a subset of JSON Schema as data. It refuses a schema that uses any keyword outside the subset, and the check then fails, so write only these.

Supported keywords: `type`, `enum`, `const`, `properties`, `required`, `additionalProperties`, `items`, `minItems`, `maxItems`, `uniqueItems`, `minimum`, `maximum`, `exclusiveMinimum`, `exclusiveMaximum`, `minLength`, `maxLength`, `pattern`, `anyOf`, `allOf`, `oneOf`, `not`.

Ignored annotations: `$schema`, `title`, `description`, `$comment`, `examples`, `default`.

Not supported: `contains`, `if`, `then`, `else`, `$ref`, `$defs`, `format`, `patternProperties`, `prefixItems`, `propertyNames`, `multipleOf`, `dependentRequired`.

- `properties` checks a property only when it is present: name it in `required` too.
- `pattern` matches anywhere in the string unless you anchor it with `^` and `$`. It has the limits of the patterns above: at most 200 characters, no backreferences or lookarounds.
- A schema holds at most 2,000 subschemas, nested at most 32 deep.

Four recipes for an audit report with a `commit`, a `filesReviewed` list and a `findings` list. Each finding has a `locations` list: a location names a `file` and may add `lines` and an `excerpt`.

**Pin a commit.** `const` holds the report to the commit the terms name.

```json
{ "id": "commit", "type": "json_schema", "required": true, "schema": { "type": "object", "required": ["commit"], "properties": { "commit": { "const": "7c1e4b9a2d3f5068a1b2c3d4e5f60718293a4b5c" } } } }
```

**Hold every location to the scope.** A finding names one location or several. `items` applies the rule to each one, so a finding with one file outside the agreed scope fails. `minItems` 1 refuses a finding that names no place in the code.

```json
{ "id": "locations", "type": "json_schema", "required": true, "schema": { "type": "object", "required": ["findings"], "properties": { "findings": { "type": "array", "items": {
  "type": "object",
  "required": ["locations"],
  "properties": { "locations": { "type": "array", "minItems": 1, "items": {
    "type": "object",
    "required": ["file"],
    "properties": { "file": { "enum": ["contracts/Vault.sol", "contracts/InterestModel.sol", "contracts/PriceFeed.sol"] } }
  } } }
} } } } }
```

**Require proof by severity.** The proof term is the deal's to set: say in the description which severities need proof-of-concept files, and hold it with this check. There is no `if`, so say it with `anyOf`: a finding is Low or Info, or it carries proof-of-concept files. That is proof for Medium or higher. To require proof from High up, add `"Medium"` to the list of severities that need none. To require no proof, leave the check out.

```json
{ "id": "proof", "type": "json_schema", "required": true, "schema": { "type": "object", "required": ["findings"], "properties": { "findings": { "type": "array", "items": {
  "type": "object",
  "required": ["severity"],
  "properties": { "severity": { "enum": ["Critical", "High", "Medium", "Low", "Info"] }, "pocFiles": { "type": "array", "minItems": 1 } },
  "anyOf": [ { "properties": { "severity": { "enum": ["Low", "Info"] } } }, { "required": ["pocFiles"] } ]
} } } } }
```

**Match a file list in any order.** Three distinct entries, each from the agreed scope, are the scope itself. Set `minItems` and `maxItems` to the number of files in scope.

```json
{ "id": "coverage", "type": "json_schema", "required": true, "schema": { "type": "object", "required": ["filesReviewed"], "properties": { "filesReviewed": {
  "type": "array", "uniqueItems": true, "minItems": 3, "maxItems": 3,
  "items": { "enum": ["contracts/Vault.sol", "contracts/InterestModel.sol", "contracts/PriceFeed.sol"] }
} } } }
```

- A report with no findings passes all four. Add `"minItems": 1` to `findings` only if an empty report is not acceptable work.
- Require only what every report of this kind has. In the worked example a location's `lines` and `excerpt`, a finding's `impact` and `status`, and the report's `summary` and `reportDate` are optional: the schema names them in `properties` and leaves them out of `required`. A buyer who needs one of them adds it to `required` before agreeing.
- The subset cannot compare two fields (a line range that ends before it starts), cannot require one property to be unique across a list (two findings with the same id), and cannot say that a finding is true.
- For what the checks cannot say, add a rubric. Judges read a report of up to 100,000 characters whole. They read a longer report as a sample of its lines, and a sampled read escalates the deal to the appeal adjudicator. The checks always run on the whole report.

A complete commitment with these checks, the full report schema and an optional five-criterion rubric is `spec/examples/commitment.audit-report.example.json` in [the repository](https://github.com/rafaeldavid/holdback/blob/main/spec/examples/commitment.audit-report.example.json).
