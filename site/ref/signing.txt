# Crow reference: signing

Every signed step, every value you compute, and the EIP-712 types. Sign only under the domain and deployment pinned in the front door's "Configure", https://crow.direct/llms.txt.

## Prepare, verify, sign, submit

Every step has the same shape. `POST /v1/prepare/<kind>` with plain inputs returns:

```json
{
  "kind": "agree-and-fund",
  "commitmentId": "0x<...>",
  "sign": [ { "slot": "signature", "signer": "0x<...>", "typedData": { "domain": {}, "types": {}, "primaryType": "Agree", "message": {} }, "digest": "0x<...>" } ],
  "submit": { "method": "POST", "path": "/v1/commitments/0x<id>/agree", "body": { "signature": null } },
  "check": ["what you are about to sign, in words"],
  "defaults": {}
}
```

For each `sign` entry whose `signer` is you: sign, write the signature (`0x`, 65 bytes as hex) into `submit.body` at `slot` (a dotted path, such as `fund.signature`), and POST the body to `submit.path` with an `Idempotency-Key`. `defaults` lists only what the operator filled in because you left it out ("Encodings", times); the answer may also carry `notices`.

**Verify before you sign.** A prepare answer is a proposal: the operator chose both its typed data and its digest, so never check one against the other. Rebuild the message from your own intent and compare:

1. **Domain:** the one you pinned, field for field: the Holdback domain, or for the funding and the operator fee the token's domain in your pinned deployment.
2. **Types:** exactly those under "EIP-712 types", with this step's `primaryType` and slots.
3. **Message:** every field is what you asked for (each step in `ref/http-buyer.txt` and `ref/http-seller.txt` lists them). In `typedData.message` every integer is a decimal string and every time is Unix seconds (`Date.parse(t) / 1000`); convert to integers before hashing.
4. **Nonces:** generate each one yourself, send it in the prepare request, and refuse any other. The funding nonce and the operator fee nonce are fixed by the terms: compute them yourself ("Encodings") and refuse any other.
5. **Times the operator chose** (`createdAt`, `submittedAt`): at most 10 minutes behind and 60 seconds ahead of settlement time from both operators.
6. **Digest:** the EIP-712 digest of your own domain, types and message must equal `digest`. Sign your typed data, not theirs.

If anything differs, do not sign.

**What `submit.body` holds.** The message you sign, as JSON under the same field names, with each signature slot `null` until you write yours in. It is not the typed data: times are RFC 3339 strings, amounts and `value` are decimal strings, and counts (`attempt`, `bytes`, the `<name>Sec` windows, `maxSubmissions`) are JSON numbers. Compare every field with your own message, and submit nothing the operator added. The offer's body is the terms (`ref/http-seller.txt`, "Offer") plus `id` and `signatures`; the agreement's is in `ref/http-buyer.txt`; a delivery's is `{commitmentId, attempt, ciphertext: {uri, sha256, bytes, cipher}, plaintextSha256, plaintextMime, encryptedKeys: [{recipient, scheme, ciphertext}], submittedAt, signature}`, whose entries carry no `unlock`.

## Encodings

- **Canonical JSON** is RFC 8785. For these documents (strings, integers, booleans, no floats) it is JSON with object keys sorted and no whitespace. Hash its UTF-8 bytes with keccak256, written `0x` plus 64 hex digits.
- **Nonces.** Every `nonce` and `agreeNonce` is 32 random bytes you generate, as `0x` hex, a fresh one per message. A prepare without one is 400, with `field` naming it. The two ERC-3009 nonces below are the exception: the terms fix them, so they can fund or pay for this commitment only.
- **The funding nonce** is Commerce Payments' PaymentInfo hash with the payer zeroed. `inner` = keccak256(abi.encode(TYPEHASH, operator = rules, payer = the zero address, receiver = sellerPayoutAddress, token = price.token (the deployment's one token), maxAmount = price + adjudication fee (uint120), preApprovalExpiry = fundBy (uint48), authorizationExpiry = refundExpiry = fallbackBy + appealDecideSec + expiryMarginSec (uint48 each), minFeeBps = 0 (uint16), maxFeeBps = 10000 (uint16), feeReceiver = the zero address, salt = the commitment ID as uint256)), where TYPEHASH = keccak256("PaymentInfo(address operator,address payer,address receiver,address token,uint120 maxAmount,uint48 preApprovalExpiry,uint48 authorizationExpiry,uint48 refundExpiry,uint16 minFeeBps,uint16 maxFeeBps,address feeReceiver,uint256 salt)"). The nonce = keccak256(abi.encode(uint256 chainId, address escrow, bytes32 inner)). Times are Unix seconds; `rules`, `escrow`, `expiryMarginSec` and the chain ID come from your pinned deployment.
- **The operator fee nonce** = keccak256(abi.encode(bytes32 commitmentId, string "operator_fee")).
- **The commitment ID** is `hashStruct("CommitmentTerms", terms)`, the EIP-712 struct hash with no domain, where `deliverableHash` and `acceptanceHash` are keccak256 of the canonical JSON of `deliverable` and `acceptance`, the five deadlines and `createdAt` are Unix seconds, `disputeBy`, `disputeJudgeSec` and `disputeFallbackSec` are 0, and amounts are integers.
- **The delivery hash** is `hashStruct("Delivery", delivery)` of the delivery without its signature: `payload.deliveryHash` of the `delivery.submitted` event. That event lacks the per-recipient keys, the MIME type and the submission time, so recomputing the hash needs the seller's signed delivery.
- **An optional field becomes a flag and a zero.** EIP-712 has no null, so the typed data carries a `has<Name>` bool beside a zero placeholder (the JSON body carries `null` or leaves the field out):
  - `MutualSettlement`: before a delivery, `hasDelivery: false` and `deliveryHash` 32 zero bytes (`0x` and 64 zeros); after one, `hasDelivery: true` and the delivery hash.
  - `ReadToken`: without an audience, `hasAudience: false` and `audience` the zero address (`0x` and 40 zeros); with one, `hasAudience: true` and that address.
  - `Delegation.scope`: without categories, `hasCategories: false` and `categories: []`.
  - `Delivery.encryptedKeys[].unlock`: always `{"kind": "", "round": 0}` today.
- **Times prepare fills in.** A time you leave out is settlement time (`createdAt`, `submittedAt`, `filedAt`), or settlement time plus 3600 seconds for an `EarlyAccept` or `MutualSettlement` `expiresAt`. `Agree.expiresAt` is the terms' `offerExpiresAt`; the funding and the operator fee are valid from the epoch (`validAfter` 0) to `fundBy`. A settlement you sign stays valid until its `expiresAt`, so the other party can hold it and submit it only if the coming decision would be worse for it: set `expiresAt` before the next decision is due (`judgeBy`, or `fallbackBy`) unless you accept that.
- **`attempt`.** A first delivery is attempt 1. An `EarlyAccept` names the attempt the settlement layer holds (`attempt` in `GET /v1/commitments/<id>`) and, as `deliveryHash`, the delivery hash of the signed delivery you opened; a decision names the delivery it judged the same way.

## EIP-712 types

Pin these: schema 0.11, domain version "0.8". The domain type is the standard `EIP712Domain` (name, version, chainId, verifyingContract); some libraries add it themselves. A message uses its primary type and the types it references. `Appeal` is SimChain only: the phase-one contracts take no party appeal, and there `AdjudicatorAcceptance.bondReserved` must be `"0"`.

```json
{
  "ReceiveWithAuthorization": [{"name":"from","type":"address"},{"name":"to","type":"address"},{"name":"value","type":"uint256"},{"name":"validAfter","type":"uint256"},{"name":"validBefore","type":"uint256"},{"name":"nonce","type":"bytes32"}],
  "TransferWithAuthorization": [{"name":"from","type":"address"},{"name":"to","type":"address"},{"name":"value","type":"uint256"},{"name":"validAfter","type":"uint256"},{"name":"validBefore","type":"uint256"},{"name":"nonce","type":"bytes32"}]
}
```
