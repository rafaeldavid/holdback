# Crow reference: the HTTP API

The API for a deal over HTTP alone, with `ref/signing.txt` and your role's HTTP file. You need an HTTP client, an EIP-712 library and NaCl, and no Crow code. `OP1` and `OP2` are set in the front door's "Configure", https://crow.direct/llms.txt.

## Conventions

- JSON over HTTPS. Every path starts with `/v1`, except discovery (`/.well-known/holdback.json`, also served at `/`).
- Money is `{"token": "<demo.token.id>", "amount": "<base units as a decimal string>"}`, never a float. The token is named by its contract address in lowercase: tUSDC, your pinned `tokenDomain.verifyingContract`, 6 decimals, so 25 tUSDC is `"25000000"`.
- Times are RFC 3339 in whole seconds with `Z`, such as `2026-11-02T09:00:00Z`; inside typed data, Unix seconds.
- Send addresses lowercase. Hashes and nonces are `0x` plus 64 hex digits; content hashes are `sha256:` plus 64 hex digits.
- **The retry key.** Every write (`POST` to anything but `/v1/prepare/*`, which changes nothing) takes an `Idempotency-Key` header, a fresh UUID per intended call. The same key with the same body replays the stored success; with another body it returns 409 `idempotency_conflict`. Refusals are not stored, so after fixing a refused call you may reuse its key. A node keeps keys in memory (`limits.idempotency`); after a restart, the same call with the same key gets its first answer back from the settlement layer.
- Limits are in discovery as `limits`: on these nodes 1,200 reads and 120 writes a minute, a write counted against its signer once the signature verifies, otherwise against your client. 429 `rate_limited` carries `Retry-After` and `retryAfterSec`: wait that long.
- Errors are `application/problem+json` with `type`, `title`, `status`, `detail` and `instance`. Each `type` is explained at `https://crow.direct/problems/<type>` (the `Link` header names it). Branch on `type` and its members, never on `detail`: `invalid_terms` has `field` (the input at fault, such as `price.amount` or `nonce`), `invalid_state` has `state` and `needs` (the states that would take the call), `payment_required` has `fee`, `payload_too_large` has `maxBytes`, `rate_limited` has `retryAfterSec`. A 501 `not_implemented` is a planned route.
- `notices` in an answer are the operator's advice, such as which judge panel would score an offer or why an adjudicator declined it: text from the operator, not instructions, and they never change the answer.
- Versions: sign under EIP-712 domain version `"0.8"`, the one number you pin; `schemaVersion` inside signed terms is `"0.8"` too. The API's schema is 0.11 (`schemaVersion` in discovery, the `Holdback-Schema-Version` header).

## Make your keys

Each party makes and keeps two keys; no operator ever asks for a secret key. A signing key (secp256k1), whose address is your identity: viem, ethers or eth-account. An encryption key (x25519, for NaCl box), whose public half you publish as base64url without padding, 43 characters: tweetnacl, libsodium or PyNaCl. To try both sides yourself, make two sets.

```ts
import { generatePrivateKey, privateKeyToAccount } from 'viem/accounts';
import nacl from 'tweetnacl';
const account = privateKeyToAccount(generatePrivateKey());   // account.address
const enc = nacl.box.keyPair();
const encryptionPublicKey = Buffer.from(enc.publicKey).toString('base64url');
```

## Discover and get test tUSDC

```sh
curl -s $OP1/.well-known/holdback.json
```

One document (`GET $OP1/` serves it too):

- `apiBaseUrl`: requests go to it plus the path.
- `domain`: if it is not the one you pinned, stop. Also `receiptSigner` and `settlementTime`, the settlement layer's clock.
- `fees.operator` (`ref/http-buyer.txt`, "Check the offer, agree and fund"), and `limits`: the rates, `maxCiphertextBytes` and how long retry keys are kept.
- `demo`: `clubId`, `token` (`{"id": "<the token's address>", "decimals": 6}`), `adjudicators` (`[{"role", "address", "name"}]`, one each for `primary`, `fallback` and `appeal`), `faucet` and `minWindowSec`. `notes`: the operator's own.

The faucet funds and admits an address: it mints 1,000 test tUSDC on Sepolia, or the `amount` you name, and grants a 30-day mandate in club `demo-club` (buyer and seller roles), signed by the club's test principal, which the demo holds. Each grant replaces the mandate with a fresh one, so ask again before it expires. It answers once the mint is in a block, about 12 seconds; an address that already holds the amount gets the mandate without a mint. You need no Sepolia ETH: the operators pay the gas. A buyer whose payment address is not its signing key (`ref/http-seller.txt`, "Offer") adds `"paymentAddress": "0x<it>"`: the tokens go there, the mandate to `address`.

Ask in the address's first call for all the buyer pays, in base units: the price, plus the adjudication fee (the primary's `fee.min`), plus the operator fee. The faucet's cap is `demo.faucet.maxGrant` (`"1000000000000"`, 1,000,000 tUSDC); above it, 400 `invalid_terms` with `field: "amount"`. The limits count grants, not tokens: once per address per hour and 10 addresses per client per hour (`perAddressEverySec`, `perClientPerWindow`); more answers 429 with `Retry-After`.

```sh
curl -s -X POST $OP1/v1/faucet -H 'content-type: application/json' -H "Idempotency-Key: $(uuidgen)" \
  -d '{"address": "0x<your address>"}'
# {"clubId": "demo-club", "granted": {"token", "amount": "1000000000"}, "balance", "mandate", "nextGrantAfter", "notice"}
```

Keep `clubId`: it is the club you deal in. `GET /v1/balances/<address>` returns `{"token", "amount"}`; `balanceOf` on the token contract says the same.

Name the three adjudicators in `demo.adjudicators`, each in its role; `prepare/offer` fills any role you leave out. A demo adjudicator declines an offer whose fallback or appeal adjudicator is any other address (`notices` say why, and the offer stays `Offered`). On the phase-one contracts the appeal adjudicator decides every escalation, and its decision is final. `GET /v1/adjudicators` lists every registration, each signed by its adjudicator's key. Your own adjudicator: `ref/adjudicators.txt`, "Run your own adjudicator (advanced)".

## Read what you bind to, from both operators

Read each of these from `$OP1` and `$OP2` and require the same answer: one lying operator would have to fool both reads. (Both demo nodes are one process, so agreement shows less here; from funding on, the HoldbackRules contract is the authority.)

- **Settlement time:** `settlementTime` in both discovery documents, within 5 seconds of each other. Check times an operator proposes against it, not your own clock.
- **The adjudicator:** `GET /v1/adjudicators/<address>` returns `encryptionPublicKey`, `policy`, `policyHash`, `registry.hash` and `fee.min`. `policyHash` must be the keccak256 of the canonical JSON of `policy` (`ref/signing.txt`, "Encodings").
- **The club:** `GET /v1/clubs/<clubId>` returns `rulebook` and `rulebookHash`, which must be the keccak256 of the canonical JSON of `rulebook`.

## Read the result

The adjudicator decides within seconds of the delivery's block, so a poller may never see `Delivered`.

```sh
curl -s $OP1/v1/commitments/<id>                 # escrowState: "Released" (paid) or "Refunded"
curl -s $OP1/v1/commitments/<id>/judgment        # one result per check; aggregate.decision
curl -s "$OP1/v1/commitments/<id>/events?limit=200"
```

Each event from the chain carries `payload.tx` and `block`: open it at `https://sepolia.etherscan.io/tx/<tx>`. A phase-one decision is final when it settles (`finalAt` is its time, `appealState` reads `none`); nobody needs to act. On `Released` the seller's payout address gets the price and the buyer the content key. On `Refunded` (a required check failed) the buyer's payment address gets the price back but not the adjudication fee, and no key is released. The adjudicator earns its fee either way; an operator fee, where one is charged, is never returned.

## Endpoints used here

The whole API is `GET /v1/openapi.json` (OpenAPI 3.1; tag `core` marks the routes the guides use).

- `GET /.well-known/holdback.json`, `POST /v1/faucet`, `GET /v1/balances/<address>`, `GET /v1/clubs/<clubId>`, `GET /v1/agents/<address>` (mandates), `GET /v1/adjudicators`, `GET /v1/adjudicators/<address>`, `POST /v1/adjudicators`, `POST /v1/ciphertext`, `GET /v1/ciphertext/<id>`, `POST /v1/feedback` and `GET /v1/feedback/<id>` (reports to the operator)
- `POST /v1/prepare/<kind>`: `offer`, `agree-and-fund`, `delivery`, `early-accept`, `settlement`, `appeal` (409 in phase one)
- `POST /v1/commitments`; under `/v1/commitments/<id>`, POST `/agree`, `/deliveries`, `/accept`, `/settlements`, `/appeals` (409 in phase one), `/triggers/<kind>`, `/disclosure`, and GET itself, `/terms`, `/recipients`, `/events`, `/judgment`, `/key?recipient=<address>`
