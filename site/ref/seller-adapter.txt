# Crow reference: the seller adapter

Every setting of the seller adapter, `examples/seller-adapter.ts`, which the seller's first hour starts.

## Sell a priced API service

For a seller that prices by quote: you already run an HTTP API with a quote call, a start call and a result call. `examples/seller-adapter.ts` in the public repo sits beside it and sells its jobs on Crow. Start it from one file: `node examples/seller-adapter.ts seller.json`, with `HOLDBACK_KEY` (your signing key) and `HOLDBACK_OPERATORS` (two or more operators, comma-separated) in the environment. Only `sellerApi` (your API's quote, start and result addresses) is required; `examples/seller-adapter.config.json` is an example, and every other field (the deal template, the scope and option rules, the terms rules, the windows, the journal) has a default. You edit no source file. It signs your offers and deliveries with that key, it never holds a buyer's key, and the operators only relay. Like the card, this is a convention, not part of the protocol.

1. **Quote.** Your card lists the item with `"pricing": {"kind": "quoted", "quote": "<url>"}`. The buyer POSTs `{"buyer": "0x<its address>", "buyerEncryptionPublicKey": "<its x25519 key, base64url>", "scope": { ... }}` to that address. The scope's fields are the seller's own; the adapter refuses a scope outside its configured rules with 400. Send an `Idempotency-Key` to get the same answer on a retry. A seller may require `Authorization: Bearer <credential>` (401 without one) and may rate-limit the route (429 with `Retry-After` in seconds); it gives each buyer its credential out of band.
2. **Offer.** The adapter asks your API for a price, fills your template's deliverable and checks with the scope, signs an offer that names the buyer (`ref/http-seller.txt`, "Offer"), and answers `{"commitmentId": "0x<...>", "price": {"token": "<...>", "amount": "<base units>"}, "fees": {"adjudication": {...}, "operator": {...} | null, "total": {...}}, "expiresAt": "<offerExpiresAt>"}`. The buyer reads the commitment by that ID from both operators and checks it as any offer (`ref/http-buyer.txt`, "Check the offer, agree and fund"): its own address and key, the price it was quoted, the checks, the adjudicators and the windows. `fees.total`, the price plus both fees, is what it funds; the answer is the seller's claim, so the buyer computes the total from the terms itself.
3. **Watch for the hold.** The adapter polls each operator's `GET /v1/commitments/{id}` every `pollMs`. It calls your start only when both operators show the commitment `Held`, with `Idempotency-Key: <commitmentId>`, so your API must return the same job for the same key. It keeps a journal file, and a restart neither starts a job twice nor delivers twice.
4. **Deliver.** When your result call returns the finished file, the adapter runs the terms' deterministic checks on those exact bytes (`ref/http-seller.txt`, "Encrypt and deliver", `check-delivery.ts`). It encrypts and delivers only when the checks accept the file or pass it to the judges. Otherwise it delivers nothing, alerts you with each failed check, and waits for your fixed report until `deliverBy`: the rules contract takes one delivery per deal, so the adapter delivers only a file the checks pass.

Your three calls, as the adapter makes them when `sellerApi` names three addresses: `POST <quote>` with `{"scope": ...}` answers `{"price": {"token", "amount"}, "quoteId", "deliverWithinSec"}` (the last two optional; `amount` is base units as a decimal string); `POST <start>` with `{"commitmentId", "quoteId", "scope"}` answers `{"jobId"}`; `GET <result>` answers 202 while the job runs and 200 with the file. `examples/seller-adapter-stub.ts` is a working stub of all three, and `examples/seller-adapter.test.ts` runs a 2,000.00 tUSD deal through both on the sim.

### Your API's shape

An API of another shape needs no service in between: describe it in `sellerApi`, and the adapter calls it as it is. `examples/seller-adapter.job-api.config.json` is a whole example, and `examples/seller-adapter-job-stub.ts` is the stub it is tested against (`examples/seller-adapter-job-api.test.ts`). Everything here is data: a placeholder is a name in double braces from a fixed list, never an expression, and nothing in the file runs.

- **Base URL.** `sellerApi.baseUrl` is the address every call goes under. Each call names a `path` under it. The adapter refuses, at start, a path that leaves it, and at run time an address that a value from your API, such as a job ID, would move outside it. It follows no redirect.
- **A credential.** `sellerApi.auth` names an environment variable, the header that carries it and an optional prefix: `{"env": "JOBS_API_KEY", "header": "Authorization", "prefix": "Bearer "}`. The adapter reads the value at start, sends it only under the base URL, and never logs it or writes it to the journal. A start with the variable unset stops and names it.
- **Each call.** `quote`, `start` and `result` each take `method`, `path`, `headers` and a JSON `body` template (`null`: no body). A placeholder is one of these names in double braces, as the example file writes them: `buyer`, `scope`, `options`, `scope.<field>` and `options.<field>` in every call; `commitmentId` and `quoteId` from the start on; `jobId` in the result. `scope` and `options` stand alone, as a whole body value; a value the buyer left out drops its key. In a path each value is percent-encoded.
- **Reading the answers.** `quote.read` takes JSON pointers to `amount` (base units as a decimal string), `token` (left out: the settlement layer's token), `quoteId`, `deliverWithinSec` and `validForSec`, how long your price holds; an offer never outlives it. `start.read.jobId` points at the job's ID, a string or a whole number.
- **One job per deal.** The start carries the deal's ID as its idempotency key, in `Idempotency-Key` or the header `start.idempotencyHeader` names, so a restart sends the same key and your API must return the same job.
- **A running job.** `result.status` is `{"by": "http", "running": [202], "done": [200], "failed": []}` (the default) or `{"by": "field", "pointer": "/run/state", "running": [...], "done": [...], "failed": [...]}`. `result.report` points at the result inside the answer, and `result.reportCall` is a second call that fetches it once the job is done. A failed job closes the deal with a `job.failed` alert, once, and is never delivered.
- **Further files.** `result.files` takes `list`, a pointer to the list of file paths inside the result; `path`, the path that fetches one, with the placeholder `file` where the file's path goes; `into`, the field that receives `[{"path", "content"}]` (absent, or the list itself); `maxCount`; `maxTotalBytes`, at most the delivery cap; and `encoding`, `utf8` or `base64`. The files are added before the report mapping and the checks run, so the checks see the delivered bytes. A repeated path, a path with an empty, `.` or `..` segment, too many files or bytes, or a file that fails to fetch holds the delivery and alerts, as a refused check run does.

- **The club and the adjudicators.** They default to the ones the operators' discovery document names (`demo.clubId`, `demo.adjudicators`). Name `clubId` and `adjudicators` in the file to choose your own.
- **A mandate.** Every offer needs a mandate in the club. On the test service the adapter takes one from the faucet at start and renews it before its 30 days end. Elsewhere your club's principal gives you one; a start without one stops and says so.
- **Removed settings.** `stream`, `host`, `trustProxy` and `quoteRateLimit.perClient` are gone (T-331). A file that sets one is refused at start, naming it, with exit code 2.
- **Price in the settlement layer's token.** `price.token` is the token ID discovery gives under `demo.token.id`: `tUSD` on SimChain, the token's address on Sepolia. The adapter refuses a price in another token and logs the one it holds.
- **The adapter signs under the settlement layer its operators serve.** It reads the EIP-712 domain from both operators and starts only when that domain is one pinned in `verify.ts`, as the buyer's signer does. It needs no chain setting of its own.
- **Run it as a service.** `examples/seller-adapter-service.md` runs the adapter behind HTTPS (Caddy in front, the adapter on the machine's loopback address) under systemd. Its `examples/seller-adapter.Caddyfile` forwards `/quote` and `/defaults`, so a card's `pricing.defaults` can name `https://<your name>/defaults`. `POST /deals/<commitmentId>/ready` is not forwarded; call it on the loopback address. In the configuration, `quoteAuth` takes the accepted credentials from an environment variable and never logs them; `quoteRateLimit.overall` sets requests per window over all clients, to any values you choose; limit per client in your proxy. A restart, a crash included, resumes every open deal from the journal with no second job and no second delivery.
- **Terms per quote.** `options` lists what a buyer may add to a quote (`{"options": {...}}`, passed on to your API); `termsRules` changes one offer from your template: when conditions on `scope.<field>`, `scope.<field>.length` or `options.<field>` hold, a rule sets windows, adds, replaces or drops checks, adds to the description, or refuses with 400 naming the fields. Rules are data and nothing in them runs. The adapter serves your defaults (the template, your windows, your scope and option rules) at `GET /defaults`; list that address on the card as `pricing.defaults`. In the template, a backslash before a placeholder keeps it as text, and `fee` sets the adjudication fee you offer. A buyer adds `"options": {"panel": true}` to a quote to have a panel of judges score the report on the template's five criteria after the checks pass: a terms rule with `"rubric": true` adds the template's `optionalRubric`, and `GET /defaults` publishes it.
- **Keep your report's own shape.** When your result is JSON in your API's own shape, set `reportMapping` to a mapping file. The adapter converts each result into your template's JSON, runs the checks on the converted bytes and delivers those. A mapping is data, never code: field paths, constants, value maps, and lists mapped item by item (`examples/report-converter.ts` lists every directive; `fixtures/data/audit-report/seller-shape-a.mapping.json` and `seller-shape-b.mapping.json` map two report shapes to the audit template). The adapter does not deliver a result the mapping cannot convert, and its log names the template field. Try a mapping on one report first: `node examples/report-converter.ts <mapping.json> <report.json>`.
- **Fix a refused report.** When the checks refuse a result, the adapter writes an `ALERT` line to its log and, with `alerts.callback` set, POSTs `{"type": "delivery.refused", "commitmentId", "deliverBy", "attempt", "checks": [{"checkId", "required", "outcome", "detail"}], ...}` to that address, signed with HMAC-SHA256 in `X-Crow-Signature` when `alerts.secretEnv` names a secret in the environment. A callback that fails or hangs never holds up a deal. Fix the report so your result call returns it; the adapter fetches it again every `redelivery.refetchEverySec` seconds, or at once when you `POST /deals/<commitmentId>/ready` with a credential from `redelivery.readyAuth`. It checks the new bytes and delivers them once they pass, never twice. The journal keeps the wait across a restart. After `deliverBy` it stops and alerts `delivery.deadline_passed`; the buyer may then reclaim. To deliver a fixed report by hand instead: `node examples/check-delivery.ts <terms.json> <file>`, then `node examples/seal.ts <journal> <file> <commitmentId>`.
- **Both halves together.** `examples/audit-deal.ts` runs this adapter and the buyer's signer (`ref/buyer-signer.txt`) through one audit-report deal: `pnpm audit-deal` on a local world, `pnpm audit-deal --live` on this test service.
- **Your own report and terms, before you sell.** `pnpm audit-deal --report <file> --terms <file>` runs the same deal on the local world with your report file and a terms file in the shape of `fixtures/terms/audit-report.yaml`. It ends Released (exit code 0) when the report passes. When your check run refuses the report, nothing is delivered, the commitment stays Held, and the run names each failed check (exit code 1). A terms file the commitment schema refuses stops the run before any deal opens, naming the field (exit code 2).
- **All of the pilot's cases.** `pnpm audit-deal --case all --report <file> --terms <file>` runs the eight cases of step 8 of the first hour in https://crow.direct/sell.txt, each through the adapter started from one configuration file and the buyer signer.
