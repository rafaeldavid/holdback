Licensing: "production deployments require a commercial agreement" (sourced). Local footprint: 4 GB RAM, 15 GB disk, about 10 GB of images, 14 host ports, Rosetta on Apple Silicon (measured, README).

**What is private from whom.** From the public and from Ethereum: everything except state roots, proofs, deposits and withdrawals. From other users: whatever the permission rows deny. **From the operator: nothing**; the proxy, the sequencer and the databases hold plaintext, and the admin role reads all of it (sourced). Matter Labs does not run the chain; the operator does, "within their own infrastructure or cloud" (sourced).

**Mapping to ADR-0001.**

| Operator power | Effect on a valid deal | What the design would have to do |
| --- | --- | --- |
| Stop the sequencer or prover | Nothing in the fragment settles; no proof reaches L1 | The L1 timeout (ADR-0007) must settle without the fragment, so the fragment is a fast path, never the settlement |
| Return 403 to one party, or revoke its permission | That party misses a deadline; the default outcome falls on it | Same; one party's stall becoming a protocol outcome is the "single party can stop" failure |
| Withhold pubdata (Stage 0 validium) | Nobody can reconstruct or prove the record | D26 evidence must live outside the fragment, as signed messages, as ADR-0024 already does |
| Read everything | Fails the 2026-11-01 requirement outright | Only an adjudicator-run instance passes (residual 6 already trusts it with plaintext), or content is encrypted before it enters, and then the fragment adds nothing over ADR-0024 |
| Filter L1-to-L2 | Blocks a party's forced entry | Harmless only if settlement never depends on entering the fragment |
| Upgrade the chain's L1 contracts | Changes what a proof means | The L1 escrow must trust only its own code and a pinned verifier (inferred) |

## 2. The institutional intraday-repo demo

**What it is (measured).** A Nuxt app over `RepoContract.sol`: a lender creates an offer, a borrower posts collateral and receives the loan, repays or loses the collateral after a two-minute grace period. Chain 6565 and chain 6566 each have their own permissions API, admin and user panels and explorer, sharing one Keycloak and one Postgres. The sequencer image is `zksync-os-server:test-only-interop-demo` from branch `sb/interop-type-b-demo`. A `cast-interop auto-relay` process holding a private key executes interop bundles on the destination chain. "Shadow accounts" let a chain-2 user act on chain 1; the SDK says they are "only available for demo purposes". USDC, TUST and SGD are `TestnetERC20Token`s minted on L2; only ETH is deposited from L1 through the Bridgehub. Permissions: the ERC-20 template marks `balanceOf`, `allowance`, `transferFrom` and `mint` as `restrictArgument` (a user reads only its own balance); every repo function is `public`. The contract has `admin`, `setAdmin`, `setGracePeriod` and `setUnbundlerAddress`.

**What it shows.** Two institutions, each on its own operator-run chain, settle a bilateral collateralized loan with per-user read privacy, across chains by message bundles (send, finalize on the source, wait for the root on the destination, execute: minutes, and relayer-dependent, not atomic). **What it does not show:** privacy from either chain's operator, or an L1-held asset released by an L2 outcome. Matter Labs' Q2 2026 report calls private atomic interoperability "architecture" and "proof-of-concept", with delivery-versus-payment as the target (sourced).

**What carries over.** (a) The one primitive a fragment would need: an L2-to-L1 message (`L1Messenger.sendToL1`, system contract `0x…8008`) proven in a batch and checked on L1 with `proveL2MessageInclusion` (Gateway era: `proveL2MessageInclusionShared` at `0x…10009`); the L1 escrow could accept `(commitmentId, outcome)` this way, tracking consumed messages itself (sourced). (b) The shape "a party reads only rows about itself", which ADR-0024's `ReadToken` already gives at the API with no chain. Not carrying over: shadow accounts, the relayer, the admin-keyed contract, L2-minted tokens.

## 3. One fragment per escrow?

**Not a supported shape** (measured, inferred). A chain is a static L1 registration (chain id, diamond proxy, Bridgehub entry; ZK Stack registration "is not permissionless"), a genesis, a sequencer with its own database, three funded L1 operator keys, a permissions API with Postgres, an identity configuration and a prover. The local stack bakes the L1 state into a snapshot and the chain id into `config.yaml`; there is no API that creates chains, and participant sets are user and role rows in the operator's database, not a property of the chain. Per-deal creation would mean per-deal L1 contract deployment (millions of gas, guessed) plus per-deal batches whose commit, prove and execute (about 460k gas of verification per batch, dated, from ADR-0024) are amortised over nothing, against a whole happy path of 395,831 gas today (measured, T-202). Latency: sub-second inside the fragment; an L1 outcome waits for a batch to be proven and executed at the operator's pace (Era posts state updates about every 57 minutes on average, measured on L2BEAT); real prover time for Prividium is unknown (the vendor claim "subsecond block proofs" is unverified).

**Realistic shapes.** (i) One shared Prividium chain per operator or club with per-deal permissions: organizations own roles and contracts, users belong to one organization, reads are filtered per caller; the operator reads everything, so this is ADR-0004's club-chosen permissioned chain with its signed residual, not a privacy gain. (ii) An adjudicator-run instance: the one party already trusted with plaintext; it passes the reading test, but it can stall, so the L1 timeout stays the settlement, and its confidentiality set equals ADR-0024 B's at the price of a chain.

## 4. Against the bar

| Shape | Same agent API? | Protocol simpler? | Strictly more private? | Removable without a protocol change? |
| --- | --- | --- | --- | --- |
| ADR-0024 B (being built) | Yes | No new actor, no gas | Ciphertext at operators; the adjudicator reads | n/a |
| Prividium fragment, operator-run | Only if the operator enrols the per-deal keys and relays, which makes it the admin | No: a sequencer actor, a proof-verification entry in the rules contract, chain registration | Less: plaintext at the operator | Only as a pure fast path; the verifier entry is an ADR and schema bump to add and to remove |
| Prividium, adjudicator-run | No: SIWE enrolment and one-hour per-transaction authorizations per key | No | Equal to B | Same |
| Shared club chain | Yes, behind the operator | No | Less | Yes, as a settlement option with a signed residual |
| Far-future ZK fragment | Yes | No, but any party may prove | More: independently verifiable | n/a |

No Prividium shape keeps the API identical while making the protocol simpler or strictly more private. The product is licensed, single-operator, `amd64`-only and served from a private registry, which would make a vendor one of the parties ADR-0001 must tolerate losing, against protocol property 3.

### 7.1 Permissions governed by an on-chain contract (Q1): no

- **Measured.** `prividium-core@77f1f59:apps/permissions-api/src/services/authorization-service.ts`, `checkMethodAuthorizationForUser`: step 2 reads `contractsTable`, step 3 reads `contractFunctionPermissionsTable` by `(contractAddress, methodSelector)` (and the contract's template), then `decidePermission` dispatches on `ruleType` (`public`, `checkRole`, `restrictArgument`, and the or/and combinations). Missing row → `permission.missing`. Role membership comes from `user_roles`; the only chain reads in the decision path are `isContract` and nonce through the target RPC (`services/transaction-classifier.ts`, `services/m2m-app-actions-service.ts`). `db/schema.ts` has no `policy_*` table: the governance "Policy" engine with approvals (`org_policy_access`, `/configuring/chain/policy`) is a closed overlay ("A narrowing authorization stage a private feature contributes at the chain boundary", `packages/api-kit/src/http/authorization-overlay.ts`) and per its docs also DB-backed ("stored in `policy_*` tables").
- **Pluggable only by forking.** `MethodAuthorizer` is "Typed as an interface so a host can serve rpcRoutes against its own engine" (same file). A Crow fork could derive rules from an L1 or L2 contract, but nothing ships.
- **Consequence for shape B.** The grain is `(contract, selector, role, signer-argument)`, not deal. Per-escrow isolation inside one escrow contract must come from the contract's own logic, executed in plaintext by the operator's sequencer. Zone-level changes (register a contract, set function rules, create roles) require `admin_write`, whose holders "must complete MFA at login" (sourced, system-permissions page) with a WebAuthn step-up on mutations (`middleware/require-step-up.ts`, measured). Org admins may only grant `org_users_manage`, `org_wallets_manage`, `org_rpc_access` (`permissions/system-permissions.ts`, `ORG_ADMIN_GRANTABLE_PERMISSIONS`). Confidence: high.

### 7.2 Admin role, multisig, removal (Q2)

- **The admin role cannot be removed or weakened.** `apps/permissions-api/src/index.ts` runs `createOrUpdateAdminRole()` at startup ("Seed the admin role once at startup"); `repositories/roles-repository.ts` upserts id `admin` with `SystemPermissions.options` (all fifteen permissions) and `isSystemRole: true`, and `onConflictDoUpdate` re-asserts the full permission set, so a direct database edit is reverted at the next boot. Updates and deletes refuse: "system roles cannot be updated", "system roles cannot be deleted" (measured). Docs on ordinary roles: "A role cannot be deleted if it is still assigned to active users".
- **It can be empty.** `CRYPTO_NATIVE_ADMIN_WALLETS` and `OIDC_ADMIN_SUBS` are optional (`env.ts`: `.optional().default([])`), and role assignments are editable, so a zone can run with no admin member. The sequencer never depends on the API, and the proxy keeps enforcing stored rows; but no principal can then register contracts, roles or users, so onboarding new escrows stops (the backlog's concern, confirmed). A zone admin can also create a role carrying only `admin_write`, but anyone with `admin_write` can re-grant `admin`, so dropping `full_read_access` from the staff role is cosmetic. `full_read_access` only governs API accounts anyway: whoever runs the sequencer holds RocksDB and the unfiltered `SEQUENCER_RPC_URL`.
- **Multisig admin: no.** Login verifies an EOA signature (`services/siwe-service.ts`: viem `verifyMessage`); EIP-1271 is used only to associate a smart-contract wallet with an already-logged-in user (`services/wallet-association-service.ts` → `services/erc1271-verifier.ts`). Admin bootstrap happens "the first time that wallet signs in" (README) or by OIDC subject; a Safe cannot log in. Multi-party control exists only as the closed Policy engine's approval groups ("An approval group is an existing role plus a threshold", sourced). On L1 the picture inverts: the `ChainAdmin` contract is "owned by the chain operator's multisig" (ownership-model page) and can be any address. Confidence: high (measured).

### 7.3 Relaying opaque payloads (Q3): yes, under a permitted selector

- **Measured**, `rpc/methods/handlers/eth_sendRawTransaction.ts`: `parseTransaction` must succeed (EIP-4844 rejected: "Unsupported eip4844 transaction"), the signer is recovered, then: `to` absent → deployment, needs `contract_deployment`; empty calldata with value to an EOA → forwarded unchecked ("A value transfer to an EOA has no method to authorize"); otherwise `checkContractAccess(signer, to, data, 'write')` → `(to, selector)` lookup. `public` and `checkRole` rules never decode arguments; `restrictArgument` calls `decodeFunctionData` against the registered ABI and a failure denies with `rule.restrict_argument.decode_failed`. So a `bytes` argument holding ciphertext passes a `checkRole` rule unread. The per-user wallet RPC additionally needs an exact prior allowance on `(wallet, nonce, calldata, value)` (`rpc/permissions/wallet-authorizer.ts`; `POST /api/wallet/transaction-authorization`, valid one hour, sourced). With the policy listener the sequencer sends each frame to `/judge` and the same tables decide "every internal CALL, DELEGATECALL, and STATICCALL" (sourced).
- **Limits.** The proxy always sees plaintext `from`, `to`, `value`, calldata; it cannot forward to an unregistered address or an unlisted selector; the EVM then executes in the clear, so ciphertext can only be stored, hashed or emitted. This is the §1 conclusion again: Prividium hides data from other users and from Ethereum, not from the operator. Confidence: high.

### 7.4 Operator separation and multi-operator sequencing (Q4)

- **Separation is a topology, not a feature.** `prividium-core` is a standalone Node service pointed at `SEQUENCER_RPC_URL`; the sequencer calls its policy listener (`POLICY_PORT`, `POLICY_AUTH_TOKEN`; sequencer side `tx_validator.policy_service.url` in `zksync-os-server@e29a2c0:node/bin/src/config/mod.rs`). Nothing binds both to one operator, and `TARGET_CHAIN_TYPE` also accepts `besu` (`utils/target-chain.ts`), where the chain is run by someone else and `/admit`/`/judge` are unavailable. Costs of a split (measured): the sequencer's raw RPC must stay private or the proxy is bypassed (deployment docs put it in a private subnet); the sequencer operator still executes and stores everything and can halt; the policy operator can halt admission, because the client is fail-closed ("Any transport, protocol-version, or response parsing error is fail-closed", `lib/tx_validators/src/policy_client/mod.rs`). Each party can stop the other; neither gives privacy from the sequencer. In the local stack the listener is off (`INSECURE_MULTI_ORG_WITHOUT_POLICY_ENABLED=true` in `docker-compose.yaml`), so the §5 probe cannot exercise `/judge`.
- **Multi-node, same operator: shipped.** `docs/src/setup/multi_node_consensus.md`: Raft `ConsensusNode`s with leader failover (crash-fault tolerant, not Byzantine), and "Batcher subsystem (L1 settlement) is not yet highly available". `docs/src/setup/batch_verification.md`: "2FA" where independent external nodes sign batch commits, optionally against a settlement-layer `MultisigCommitter` whose validator set and threshold bind the commit path; "Unavailable ENs therefore stall the batch pipeline". That is a multi-party check on commits with a liveness cost, not multi-operator sequencing. L1 validator roles (`PRECOMMITTER`, `COMMITTER`, `REVERTER`, `PROVER`, `EXECUTOR`) rotate through `ValidatorTimelock` (`era-contracts@96d41f2`).
- **Decentralized sequencing: roadmap.** Q2 2026 report: "Protocol work continued on Stage 1 decentralization support", no detail; the censorship fallback is Priority Mode (§7.5). Confidence: high on what ships, low on timing.

### 7.5 Validium data availability, exit, forced inclusion (Q5)

- **DA (measured).** `zksync-os-server@e29a2c0:lib/types/src/pubdata_mode.rs`: `PubdataMode { Blobs, Calldata, Validium }` with `Validium → DACommitmentScheme::EmptyNoDA`; the mode is read from L1, not config (CHANGELOG: "use validium-rollup setting from L1 - not config"). ZK Stack docs: a Stage 0 validium "only stores its pubdata in the database of the node(s) running the chain"; Stage 1 and 2 post to Avail, Celestia or EigenDA with optional inclusion proofs. Prividium docs: "Only the state roots and zero-knowledge proofs are posted to Ethereum", and do not say which stage production chains run.
- **Exit when the operator stops.** A withdrawal needs an L2 inclusion plus commit, prove and execute on L1 (`facets/Executor.sol`, `onlyValidator`), then `finalizeWithdrawal` with a log proof. L2BEAT on the same stack: "Only the whitelisted proposers can publish state roots on L1", so withdrawals freeze. On a Stage 0 validium nobody else holds the state to build a batch at all.
- **Forced inclusion today.** L1→L2 priority transactions exist (`facets/Mailbox.sol` `_requestL2Transaction`, `PriorityTree`), behind the optional filterer (`Admin.setTransactionFilterer`, `onlyAdmin onlyL1`; Prividium's filterer lets a non-whitelisted EOA "deposit only to its own address"). Once queued they are FIFO and unskippable at block build (`lib/sequencer/src/execution/execute_block_in_vm.rs`: "the FIFO cannot skip it"), and L1 checks only that the count and rolling hash match what L2 processed; the operator may process none. L2BEAT: "Users can submit transactions to an L1 queue, but can't force them". `PRIORITY_EXPIRATION = 0 days` on `main` and on tag `zkos-v0.30.2` (`common/Config.sol`). Inferred from the same block-build code: a priority transaction the policy service denies is a "genuinely invalid priority tx" that dumps the block rather than being skipped, so the permissions API cannot silently censor an L1 entry, it can only stall the chain; not verified end to end.
- **Priority Mode (v31 line, sourced and measured).** `era-contracts@draft-v31:common/Config.sol`: `PRIORITY_EXPIRATION = 4 days`, "Maximum time a priority transaction may remain unprocessed before Priority Mode (escape hatch)"; `state-transition/validators/PermissionlessValidator.sol` exists. Developer discussion #1156: "anyone may call `activatePriorityMode()` on the chain's L1 contract"; then "batches may contain only transactions from the priority queue" and anyone settles them through `PermissionlessValidator`; "Priority Mode is an opt-in feature" (`permanentlyAllowPriorityMode`), "for ZKsync OS chains that settle directly on L1". The discussion "says nothing about data availability or validium chains", so whether a priority-only batch can be built and proven on a validium without the operator's state is **not in public docs**. Confidence: high on mechanics, none on validium exit.

### 7.6 L2 outcome to L1 release; latency and gas (Q6)

- **Path (measured).** L2: `system-contracts/contracts/L1Messenger.sol` `sendToL1(bytes calldata _message) returns (bytes32)` at `0x…8008`; L1: `facets/Mailbox.sol` `proveL2MessageInclusion(batchNumber, index, L2Message, proof)` (lines 91 to 98 at `96d41f2`; `proveL2MessageInclusionShared` for the shared `MessageRoot`), valid once the batch is executed. The L1 escrow calls `IMailbox(diamondProxy).proveL2MessageInclusion(...)` and tracks consumed `(batch, index)` itself, as §2(c) proposed. In Prividium, `L1Messenger` is auto-registered with `sendToL1` in its ABI ("Sends withdrawal messages to L1", `services/system-contracts/registry.ts`) and "Sync creates no permission rules; functions without rules default to Forbidden", so the operator must grant `sendToL1` (or the escrow contract's function with Umbrella) to the parties' roles, and may revoke it. Add `ValidatorTimelock.executionDelay` (owner-set; Era runs "1d execution delay" per L2BEAT).
- **Latency.** Batch seal by `batcher.batch_timeout` (1 s locally; config doc: "On mainnet environments with low load, consider a higher value (e.g. 3 hours)" because "L1 settlement has a non-trivial gas overhead per batch"), then FRI and SNARK proving, then commit, prove and execute with 3 confirmations by default (`lib/l1_sender/src/config.rs`). Era reference: state updates "typically occur every 57m 5s on average" (L2BEAT). Airbender marketing: "~35 s" per Ethereum block on one H100 and "sub-second block proofs", which the same page's table contradicts; unverified.
- **Gas.** Not in public docs. The sender estimates with `eth_simulateV1` and falls back to `L1_GAS_LIMIT_FALLBACK = 15_000_000` per transaction (`lib/l1_sender/src/lib.rs`), a cap, not a cost. The dated Era figure (about 460k gas of verification per batch) stands; `proveL2MessageInclusion` cost is unmeasured. Confidence: high on path, none on numbers.

### 7.7 Private atomic interoperability (Q7)

- **Public description.** Talk transcript (Matter Labs CEO, 2026-07-21): the parties agree and simulate the exchange, sign the intent and its effects, post a hash commitment to a neutral data-availability layer with Ethereum as settlement, lock assets in escrow contracts on both zones, each chain commits its state root to Ethereum, the happy path releases when the commitment is confirmed, and if it is not posted by a set Ethereum block "they will revert and go back to the pre-agreed release path". Q2 2026 report: "We advanced the architecture for private atomic interoperability" and "Multi-prover proof-of-concept work completed". Marketing (ZKsync Connect): "neither leg is cleared to execute unless both are"; "Only cryptographic commitments posted on Ethereum → full privacy". `era-contracts` carries work branches `ad-atomic-interop-da-contracts`, `atomic-imt-interop-release`, `dz-v32-atomic-v8-settlement` (names only, measured), so the v32 line is where it lands.
- **L2 outcome releasing an L1 asset.** Not described anywhere public: the design is zone-to-zone with Ethereum as the commitment and settlement layer; an L1-held asset still goes through §7.6. It is close to Holdback's own shape (signed commitment, timeout, default outcome), but with escrows on both chains, so the "fast path only" rule from §1 still applies. Confidence: medium.

### 7.8 Machine clients (Q8): three browser-free paths, all measured

1. **Per-key SIWE session.** `POST /api/siwe-messages` → sign → `POST /api/auth/login/crypto-native` → bearer token (`routes/auth-routes.ts`; `USER_SESSION_DURATION_SECONDS` default 3600; docs: "There is no dedicated refresh endpoint"). Then `POST /rpc` with `eth_sendRawTransaction`: the proxy recovers the signer, requires it to be one of the user's wallets (`wallet.not_owned_by_user`), checks `(to, selector)` and forwards. No per-transaction authorization on `/rpc`; that exists only on `/rpc/wallet/{token}`, which "should only be used as an RPC URL in a user wallet application". Passkey-protected admins are "not suitable for programmatic RPC access". The key must already be associated with a user.
2. **M2M application.** API key in `x-api-key` (`middleware/api-key-auth.ts`; hashed, expiring, revocable) with a mandatory IP allowlist: "When the IP whitelist is empty, API-key authentication is rejected from all IP addresses"; CIDRs wider than /16 refused unless `INSECURE_M2M_ALLOW_ANY_IP_ENABLED`. With `org_rpc_access` the app may call `/rpc`, including `eth_sendRawTransaction`, for any wallet of a user in its linked organizations; the **user's** roles decide, not the app's (`rpc/permissions/rpc-authorizer.ts`, `m2m_app` branch).
3. **Service-account onboarding.** `org_users_manage` and `org_wallets_manage` let the app create users with the organization's default roles and attach wallets that must be "fresh EOAs": unregistered, nonce 0, not a contract (`services/m2m-app-actions-service.ts`, `validateNewWalletAddresses`). This fits ADR-0024's per-deal keys exactly. Limits: `MAX_WALLETS_PER_USER`, `MAX_ORGANIZATIONS`.

Not available: OIDC client-credentials (OIDC is human login); tenants and services are "legacy and will be removed". Confidence: high.

### 7.9 Mainnet chain creation and Gateway (Q9)

- **Who signs.** `era-contracts@96d41f2:l1-contracts/contracts/bridgehub/Bridgehub.sol`: `createNewChain(...) external onlyOwnerOrAdmin ... onlyL1`; `registerSettlementLayer` and `addChainTypeManager` are `onlyOwner`. Ownership docs: the Bridgehub is "Owned by the ProtocolUpgradeHandler" (ZKsync governance); the shared-bridge docs: "registration is not permissionless", with an ecosystem-admin multisig able to create chains. So a chain in the shared mainnet ecosystem needs Matter Labs' or governance's signature. The CTM "might have multiple instances with different ownership", and the contracts are MIT, so an own ecosystem is deployable, but no public doc says Prividium supports or licenses that.
- **Time and L1 cost.** Not in public docs (the quickstart covers only local runs; `zkstack chain init` "uses the ecosystem's governance to register the chain"). Which ecosystem Cari or Memento register in is not published.
- **Gateway.** "ZKsync Gateway is now deprecated"; "All ZKsync Chains that previously used Gateway for settlement have been migrated to direct L1 settlement"; new chains "must initially launch with Ethereum as their proof submission origin". No Gateway option today; Priority Mode is defined for chains "that settle directly on L1". Confidence: high on signers and Gateway, none on time and cost.

### 7.10 Licensing, arm64, prover hardware (Q10)

- **Licensing.** `prividium-core` is Apache-2.0 (`LICENSE.md`, `NOTICE`: "Prividium Core, Copyright 2026 Matter Labs"), covering the permissions API, RPC proxy, policy listener, SDK and CLI (`prividium proxy`, `prividium doctor`). README: "It is not the full commercial offering"; the admin and user web applications, deployment and operations tooling and the managed service are excluded, and "Use of the Prividium name for modified or redistributed versions requires written approval". The Block (2026-09-08) quotes Matter Labs that an institution could "operate a permissioned chain from public code in its own environment" and that "Administration tools and integrations into an institution's existing systems will remain commercial products". Still in the docs source (`zksync-docs:content/10.zk-stack/35.prividium/_partials/_license-callout.md`): "production deployments require a commercial agreement"; the private explorer needs a licence. Closed in practice: `prividium-adminv2`, `prividium-user-panel`, `prividium-stack-tools`, `webhook-service`, the demo images, the Policy engine with approvals and asset instructions (referenced only by env vars and overlay hooks). The admin API is REST with Swagger at `/docs`, so panels are replaceable by scripts. Net: a third party can run sequencer, contracts, prover and permissions engine with no agreement and no vendor registry; the protocol's property 3 objection in §4 shrinks to the trademark and the closed extras.
- **arm64.** Every Matter Labs image in `local-prividium@42616e8` is pinned `platform: linux/amd64` (`prividium-adminv2`, `prividium-permissions-api`, `prividium-user-panel`, `prividium-stack-tools` v1.312.0, `zksync-os-server` v0.24.5, `webhook-service` v0.1.28, the ghcr block-explorer images). `zksync-os-server`'s CI builds a single-arch image (`.github/workflows/docker.yml`, no `platforms`) but publishes release binaries for `aarch64-unknown-linux-gnu`, `aarch64-apple-darwin` and `universal-apple-darwin` (`release-bins.yml`); `prividium-core` has no Dockerfile in the public tree and is plain Node 22. So native arm64 is a matter of building the open parts; only the closed images force emulation.
- **Prover hardware.** `zksync-airbender-prover` README: the FRI prover "currently requires a GPU (at least 24GB of VRAM)"; the SNARK prover "requires around 140 GB of RAM - and GPU"; `zksync-airbender/docs/gpu.md`: "final proofs are still done on CPU (as they require 150GB of RAM)"; `docs/end_to_end.md` distinguishes 24 GB and 32 GB VRAM tiers. Marketing: "Airbender reaches 21.8 MHz on a single H100 GPU", "From RTX 4090s to H100s". Prividium's deployment page only says "prover farm of CPU/GPU workers that can auto-scale". Per-batch proving time and cost on a Prividium chain: not in public docs. Confidence: high on requirements, none on cost.

### 7.11 What this changes for Candidate shape B

- Per-escrow RBAC "derived by code" is possible for **users and keys** (M2M `org_users_manage`, `org_wallets_manage`, fresh EOAs) but not for **contract rules**, which need an MFA-gated `admin_write` session; and the model is per role and selector, not per deal, so deal isolation lives in the contract, executed in plaintext by the sequencer (§7.1, §7.3).
- "Burn the admin keys" is not available on the API: the `admin` role is immutable and re-created at boot; emptying it freezes onboarding (§7.2). On L1 the chain admin can be a multisig or renounced.
- The operator reads everything regardless of roles; separation of the API operator from the sequencer operator trades one halt power for two (§7.4).
- The settlement primitive exists and needs an operator-granted permission plus the batch pipeline; the escape hatch (Priority Mode) is v31-line, opt-in, and unanswered for validiums (§7.5, §7.6).
- The licensing and vendor-registry objection is mostly gone for the core; the arm64 objection reduces to the closed images (§7.10).

1. **Validium exit under Priority Mode.** On a Stage 0 validium (`EmptyNoDA`), can anyone build and prove a priority-only batch after `activatePriorityMode()` without the operator's state? Do Cari and Memento enable Priority Mode, and which DA stage do they run?

3. **Private atomic interoperability.** The concrete protocol beyond the talk (who posts the commitment, how both zones observe it, timeout bounds), whether an L1-held asset can be released atomically by an outcome on a Prividium chain, and the target release (v32?).
4. **Mainnet chain creation.** Steps, elapsed time, L1 cost, and who signs for a chain in the shared Bridgehub; whether an own ecosystem (own Bridgehub and CTM) is a supported and licensed Prividium topology.
5. **Closed components.** Whether the admin panel, Policy engine with approvals, asset instructions and stack tools are required for a supported production deployment; their terms for an open-protocol operator; arm64 image plans.
6. **Sequencing outside one operator.** Stage 1 scope and timing; whether the API-operator / sequencer-operator split is a supported topology; whether an EIP-1271 principal (multisig) can hold `admin_write` or be an org admin, or whether approval groups are the intended multi-party control.

## Appendix: the original proposal (moved from `docs/backlog.md`, 2026-11-03)

This was the backlog section "Exploration: a single-use Prividium fragment per escrow". It is kept here as written, as the question this research pass answers, with its references to this file adjusted; the backlog now links here.

Proposed by Rafa on 2026-11-01. To explore with T-207 (private deals), after the Phase 2 contracts exist on Sepolia. Not a decision: a research and spike task.

**Sources (Rafa, 2026-11-02).** Matter Labs' local Prividium stack, https://github.com/matter-labs/local-prividium (Docker Compose: Prividium API with permissions and protected RPC, admin and user panels, Keycloak, PostgreSQL, a zkSync OS sequencer, an Anvil L1, block explorer, webhooks, metrics; images from a private quay.io registry, credentials `PRIVIDIUM_DOCKER_USERNAME` / `PRIVIDIUM_DOCKER_PASSWORD` in `.env`, login with `pnpm prividium:login`), and an institutional demo with an intraday repo flow, https://github.com/JackHamer09/prividium-institutional-demo#intraday-repo.

**Research pass (2026-11-02): recommend park, pending Rafa.** This document: Prividium is a single-operator permissioned validium; its admin can read the whole chain, bypass permission checks, halt the sequencer and withhold data, so it is private from outsiders but not from its operator (fails D4's 2026-11-01 requirement and ADR-0001 unless the L1 timeout carries every deal). One chain per escrow is not a supported shape (no chain-creation API; per-batch L1 verification would cost more than today's whole deal). The realistic shape is a shared chain with per-deal permissions, which is ADR-0004's club-chosen chain. No shape keeps the agent API identical while making the protocol simpler or more private. An optional half-day local probe and its pass/fail criteria are in §5; Docker is not on Rafa's Mac, and a cloud-environment check is under way.

**Candidate shape B (Rafa, 2026-11-02): one Crow-operated Prividium, RBAC per escrow, multisig admin, admin keys burned later.** Crow runs one shared Prividium; each new escrow gets roles for exactly its buyer, seller and named adjudicators; a multisig holds the admin role; the operator only sets up what each escrow needs; once it works, the admin keys are burned. What it would take to pass the litmus tests:
- **Assets stay in the L1 escrow** and every L1 timeout works without the Prividium, so the chain is a private execution and evidence venue, never custody (ADR-0002, ADR-0001: a halted sequencer must not stop settlement).
- **Per-escrow permissions derived from the signed terms by code**, not granted by an admin API call: otherwise burning the admin keys also freezes onboarding of new escrows. Open question for Matter Labs: can permissions be governed by an on-chain contract?
- **Burning the admin role is not burning the operator.** The sequencer and prover keys (commit, prove, execute on L1) stay with whoever runs the chain, and the sequencer executes every transaction in the clear, so Crow would still read every deal and could halt or censor, against D34 (the operator does not read the deal) unless deal payloads stay encrypted end to end as in ADR-0024, which removes most of Prividium's benefit. Open questions: can the chain run with no `full_read_access` role, with the admin role removed, and with sequencing outside Crow?
- **The multisig's signers must be independent of Crow** (ADR-0001 counts Holdback's own maintainers as one party).
- **Simplicity:** agents must see the same API, and removing the Prividium must not change the protocol (the bar above).
What it would add over ADR-0024 on L1: amounts, addresses and timing hidden from the public. The local probe in §5 tests exactly these points (per-escrow permissioning, admin removal, what the operator can read).

**Bias to simplicity (Rafa, 2026-11-02).** The goal is an elegant, simple, unified API over a hard protocol. Adopt a fragment only if agents still see the same API and the protocol gets simpler or strictly more private for the cost; a stack that adds an identity provider, databases or a permissioned sequencer to every deal fails that bar unless it can be hidden entirely behind the operator API and removed without changing the protocol.

**The idea.** Each escrow runs inside its own short-lived private instance built from shared Prividium architecture, whose only participants are the two parties and their named adjudicators. The deal's content, negotiation and judgment happen there, unseen by operators or anyone else. The assets never leave Ethereum mainnet: they sit in the L1 escrow contract, which releases or refunds as a byproduct of the fragment's proven outcome. When the deal is final, the fragment is retired.

**Proposed architecture.**

| Layer | Where | What it holds or does |
| --- | --- | --- |
| Assets | Ethereum mainnet: the escrow rules contract (Phase 2, no admin keys) | USDC or any asset, locked at funding. Releases or refunds only on a valid proof of the fragment's outcome, or on a permissionless timeout trigger (reclaim, default) |
| Deal | One Prividium fragment per escrow | The terms, messages, deliveries and the judgment record; participants are the buyer, the seller and the adjudicators named in the terms; operators relay, but cannot read |
| Shared infrastructure | Prividium (shared prover, sequencing and data services) | Instantiates fragments on demand, proves each fragment's final state to L1, and keeps per-fragment state isolated |
| Bridge of outcome, not of assets | The L1 contract verifies the fragment's proof | Only the outcome (release, refund, split, default) and a commitment to the private record cross to L1 |

**Lifecycle.**

1. **Open:** the parties agree the terms. The L1 contract records the commitment hash, the hold and the deadlines, and a fragment is created with only the named participants.
2. **Run:** offers, delivery, the adjudicator's private judgment and any appeal happen inside the fragment.
3. **Settle:** the fragment proves its final state. The L1 contract verifies the proof and moves the assets once: release, refund or the agreed split.
4. **Fall back:** if the fragment stalls past a deadline, anyone can trigger the L1 timeout path (reclaim or default) without the fragment. No sequencer or operator can block settlement.
5. **Retire:** the fragment closes. Each party keeps the signed private record, and L1 keeps the commitment to it (D26 evidence).

**What it must show to pass the litmus tests.**

- **Neutrality:** no fragment operator, sequencer or prover can stop a valid deal or move held funds outside the terms. The L1 timeout path works with the fragment offline (a `neutrality.` fixture).
- **The hold:** funds stay locked in the L1 contract, which has no admin keys, and move once.
- **Defended judgment:** the panel runs inside the fragment with the same defenses, and the proof binds the judgment record hash.

**Questions to answer.**

- Which proof the L1 contract verifies, and the gas cost per deal on mainnet (with D33's fee in mind).
- What stays public on L1: the funding and payout transfers show amounts and addresses unless the token is confidential. That needs its own answer (confidential tokens, or a shielded pool).
- Who sequences each fragment (a party, the adjudicator or a neutral prover), and how either party forces the outcome or a default to L1 if it stalls.
- Spin-up time and cost per fragment, against deal size, and how many fragments the shared infrastructure can run at once.
- Data availability: where the private record lives after retirement, and how each party and a court can verify it later.
- Whether Prividium supports ephemeral, per-escrow participant sets today, or what it would take.

**Deliverables of the exploration.** A short design doc and an ADR draft; a spike on Sepolia showing one deal settle on L1 from a fragment's proof, including the stalled-fragment timeout path; measured gas, latency and cost per deal; a recommendation on whether to adopt it for T-207.
