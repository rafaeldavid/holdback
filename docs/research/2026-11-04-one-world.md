## The question

T-220 ships round 1's prerequisites to the live demo. Its task file says the deploy starts a fresh Sepolia world: "The world rebuilds its rulebook from code each time it opens, and every open deal is bound to the old rulebook's hash, so a rulebook changed in place would no longer match them (inferred)" (`docs/tasks/T-220-ship-round-1-prerequisites.md:15`). A fresh world costs three things:

- the API stops showing earlier deals (they stay on chain);
- monitoring history breaks;
- the three demo adjudicators need three new 25,000 tUSDC bonds.

Rafa wants one long-lived world. Can one world absorb each kind of change, and what does that take?

## Summary

**Recommendation for T-220: keep `holdback-public-demo-sepolia-2026-11-04`.** Change the demo club's rulebook in place and hand the demo adjudicators the drand source. No new world name, no new keys, no new bonds. Measured in a scratch test on 2026-11-04: a stored deal keeps the club it was offered under (`Book.club`), moves on from its book under the new club, and a new offer still bound to the old hash is refused with `rulebook_unknown`, whose text tells the agent to read the club again. The inferred sentence in T-220's Intent is right for the SimChain world, which replays its offers on open, and wrong for the Sepolia world, which replays nothing.

Per change kind:

1. **A rulebook change.** One world absorbs it with no multi-rulebook code. The rulebook is read from the world's club in one step only, the offer; every later step reads the book. Old deals keep their rulebook; new offers bind the new hash (measured).
2. **A schema bump.** An additive bump (0.9 to 0.10) changes no stored row, and the Sepolia world replays nothing on open (measured). The `docs/operations.md` rule "a schema bump resets the public world" describes SimChain's journal and the 2026-11-02 incident. A bump that moves the EIP-712 domain needs a contract redeploy first, which is case 4.
3. **The code changes.** None forces a reset. T-217 reads a state without `beaconSource` as `sim` (measured by its tests). T-218 seeds `chainTxs` from the stored events and reads the logs from the deployment block on its first pass (inferred from its Handoff and `sync.ts`). T-219 and T-221's store add rows (inferred from their designs). T-218 cannot rebuild old deals from the chain's logs: it applies transactions only for deals it holds a book for.
4. **A contract redeploy** is the one legitimate reason for a new world. The world refuses to open against another rules address (`apps/demo-cloud/src/world.ts:306`), a new `HoldbackRules` is a new EIP-712 domain every signature is checked under, and its constructor creates a new bond vault. One world over two contracts means a settlement facade in the money path; not worth it before mainnet. History then lives in the chain, in the old world's storage (never deleted) and in the deploy record; a read-only archive route is a backlog row.
5. **Keys and bonds.** Cases 1 to 3 keep both. Case 4 needs three new bonds in the new vault whatever the world does; the keys survive only if the world does. A world key seed, set once as a Worker secret, would keep the adjudicators' addresses across worlds (an option for Rafa).

**Standing rule:** a new world only for a new rules contract or another chain. Everything else changes in place.

## What a world is (measured)

- One Durable Object, class `World` (`apps/demo-cloud/src/worker.ts:89`), shared by both operator Workers; holdback-op2 binds holdback-op1's class by script name (`wrangler.op2.jsonc`). The Worker picks the world by name from `WORLD_NAMES` (`worker.ts:59`) according to its `SETTLEMENT` variable, `sim` or `sepolia`.
- On first open the world writes `meta` (`world.ts:91-101, 300-303`): a random 32-byte `secret`, `start`, `minWindowSec`, `settlement`, the lowercase `rules` address and, as setup goes, `bonded`. Every key the world holds derives from `secret` and a label (`world.ts:308`): the club operator, the club principal that signs faucet mandates, the three adjudicators (signing and encryption keys), the two receipt signers and the fee address. No route serves any of them (`world.test.ts:113`).
- On every open it checks `meta.settlement` against the Worker's and `meta.rules` against the embedded deployment, and throws otherwise (`world.ts:305-306`; the second message ends "a new deployment needs a new world").
- It rebuilds the club from code on every open: `SIM_RULEBOOK` with the stored `minWindowSec`, the token rebound to tUSDC's address (`world.ts:321-322`). The club's `rulebookHash` is keccak256 of the rulebook's canonical JSON (`packages/core/src/canonical.ts:42`).
- The Sepolia world's rows: `meta`; one book per commitment under `b:<id>` (the signed offer, acceptance and agreement, the delivery and its envelopes, nonces, idempotency replays: `Book`, `packages/settlement/evm/evm-settlement.ts:108-129`); event pages of 64 under `e:`; mandate pages under `mp:`; ciphertexts, the encrypted deliverables, under `ct:<sha256>`; judgment records under `jr:<id>`; faucet windows under `fa:<address>` and `fm:<day>`; the request log under `rl:<hour>`; usage under `tm:current`; the live-judge budget under `lj:<day>`. T-218 adds `cursor`, T-219 adds `lane:<n>`, T-221 slice 2 adds `ar:<address>`.
- On open it calls `EvmSettlement.restore` with the books, events and mandates (`world.ts:341-345`; `evm-settlement.ts:286-307`). Restore copies each book, rebuilds the nonce set and the idempotency map, and checks the event sequence. It applies no submission and reads no club. The SimChain world instead replays its journal through `submit` (`packages/settlement/sim/simchain.ts:394-411`), so every old offer is checked again under the current genesis. That difference decides everything below.

## Findings

### 1. A rulebook change (T-217: `randomness: { source: 'drand-quicknet', chainHash }`)

**Measured.**

- The rulebook is looked up in the world's clubs in exactly one step: the offer. `evm-settlement.ts:702` finds the club by `(clubId, rulebookHash)`, and core's `offer` refuses when none matches or the supplied rulebook hashes differently (`packages/core/src/state.ts:175-176`). SimChain does the same (`simchain.ts:692`). PR 185's late-joined offer uses the same lookup.
- The book stores the club (`Book.club`, `evm-settlement.ts:110`, written at `:710`). Every later step reads the book: the buyer's scope and membership at agree and fund (`:846, :849, :888`), the appeal bond rate and fee, the mutual-settlement rule and the default outcome (SimChain's `rec.club.rulebook`, `simchain.ts:767-979`). `admit` checks only the club id (`evm-settlement.ts:386`).
- **Scratch test** (`packages/settlement/evm/one-world.scratch.test.ts`, run once in the main checkout, then deleted; 1 test, passed in 200 ms, 2.44 s in all). Against a chain double with no network: an offer lands under the sim rulebook; the settlement is drained and restored under a club whose rulebook names `drand-quicknet` (same id, new hash); the stored deal reads `Offered` with the old hash while no club in the new genesis matches it; the primary's acceptance is applied from the book (`AcceptedByAdjudicator`); a new offer bound to the old hash is refused `rulebook_unknown` ("no rulebook registered for 0x5bb3…988e"); a new offer bound to the new hash is accepted. The double saw five reads, `balanceOf` and `freeOf`, and nothing was sent.
- The operator serves the first club with the id: `GET /v1/clubs/{id}` (`apps/operator/src/server.ts:998`) and prepare (`server.ts:907`, `prepare.ts:299, 327`) use `reg.clubs.find((c) => c.id === id)`. The problem text already names the fix: "Read the club (GET /v1/clubs/{id}) and bind its current rulebookHash" (`apps/operator/src/problems.ts:29`).
- The adjudicators read the beacon source per commitment from the stored state (PR 186, `apps/adjudicator/src/simchain-adapter.ts`, `randomness(c)`: `escrowState(c.id).beaconSource ?? 'sim'`; `service.ts` `#preflight`). An old deal keeps `sim`, a new one gets `drand-quicknet`. For an old deal's fallback or appeal the service signs a `sim` beacon that the contract refuses, so such a deal still ends in the default outcome. That is today's limit, kept only for deals opened before the switch.
- The contract never reads a rulebook. `rulebookHash` is a field of the signed terms, hashed into the commitment id (`packages/core/src/eip712.ts:109`, `packages/settlement/evm/encode.ts:59`). Old and new deals coexist on chain under different hashes.
- Crow's test seller reads the hash fresh for each offer (`apps/test-agents/src/seller.ts:504`, `examples/agent.ts:87-92`), so it needs no change.

**What breaks, and what to do.**

- Discovery: nothing. It carries `clubId`, never the hash (`world.ts:401-419`).
- Prepare: serves the new hash as soon as the code is live.
- An offer prepared before the deploy and posted after it: 422 `rulebook_unknown`, with the next step in the problem. No grace period: keeping the sim rulebook beside the new one would let new Sepolia deals bind a rulebook whose fallback and appeal cannot decide. One current rulebook per club.
- The SimChain world keeps `sim`. PR 186's parse rule admits a drand club anywhere, and SimChain then refuses every drand-proven decision (T-217 Decisions 4; its backlog row). `world.ts` names drand for the live world only, as T-217's Handoff says.
- `MIN_WINDOW_SEC` is pinned in `meta` for SimChain's replay (`world.ts:298-299`; `docs/backlog.md:276`). The Sepolia world needs no pin: a window change is a rulebook change, and finding 1 covers it. Moving the pin is a one-line follow-up, not T-220's.

**Inferred.** This is the first in-place rulebook change on a chain world: ADR-0024's fields (2026-11-01) and the 0.9 move (2026-11-04) each came with a new world. The measured path above is the whole path, so no untested branch remains.

### 2. A schema bump (T-221: 0.9 to 0.10)

**Measured.**

- `SCHEMA_VERSION` is a string the operator serves (`server.ts:61`; PR 184 moves it to `'0.10'`). The 0.10 changes are a new message type, an optional `registration` envelope on the adjudicator record and every `$id` (PR 184, `spec/README.md` changelog). `commitment.schemaVersion` stays `'0.7'` and no typed-data struct changes, so no stored book, event or terms object changes shape.
- `restore` replays nothing (`evm-settlement.ts:286-307`), as ADR-0028 §5 says. `docs/operations.md:68` ("A schema bump resets the public world. The World replays its journal on start…") describes the SimChain world and the 2026-11-02 incident: v0.8 added rulebook fields, the journal replayed v0.7 offers through `submit`, and the lookup at `simchain.ts:692` found no club. The Sepolia world has no such path, and the scratch test above reopened a book under a changed club.
- `Meta` records no schema version (`world.ts:91-101`). A world cannot tell which build wrote its rows; today nothing needs to.

**Inferred.**

- A 0.9 book reads under 0.10 as plain data: `restore` structured-clones it, the views are built from it, and the API's responses are checked against the schemas in tests, not on the serving path. T-217's tests already show an older state (no `beaconSource`) reading under newer code (PR 186 Evidence).
- A schema bump that changes a signed struct moves the EIP-712 domain (the v0.7 rule in `spec/README.md`), and `LiveChain.verify` refuses a contract under another domain (`packages/settlement/evm/live.ts:57-60, 218-222`). Such a bump needs a contract redeploy first, which is finding 4. So: additive bump, same world; domain bump, see finding 4.
- T-221 slice 2 is already written against one world: "it creates the `ar:` rows on the first open after the deploy, and each later open re-registers idempotently … Do not change `WORLD_NAME` for schema 0.10" (PR 184, T-221 Handoff, step 2).

### 3. The code changes (T-217, T-218, T-219, T-221)

- **T-217 (PR 186), measured by its tests.** `beaconSource` is new in every state. A state saved before it has none, and `beaconClockOf(undefined)` reads it as `sim` (PR 186 Decisions 1 and Evidence). No reset. The one-line change for the world is in its Handoff: `drand: drandQuicknet()` for the live world's adjudicators, and the rulebook line for the live world only.
- **T-218 (PR 185), inferred from its Handoff and `sync.ts`.** Books saved before it have no `chainTxs`; `restore` seeds them from the events' `tx` ("Books saved before T-218 have no chainTxs: their events name the transactions applied", PR 185 `evm-settlement.ts`). The live world has no `cursor` row, so the first pass reads every rules-contract log from block 12061237 to the head in one `eth_getLogs` call (fewer than 50,000 blocks), fetches only the transactions of deals it holds books for and has not applied, and should apply nothing (T-218 Handoff for T-220). No reset.
  - Can the sync rebuild a world's view of old deals from the logs? No. `ChainSync.read` fetches a transaction only when `evm.follows(id)`, that is, when the node holds a book; a commitment without one is counted as `unknown` and skipped (`sync.ts`, `read`). A party can make a deal join by posting its signed offer (T-218 Decisions 4). The logs are an archive of the chain's view, not of the API's.
- **T-219 (no PR; Status todo), inferred from its design.** One `lane:<n>` row per lane, written before a broadcast and deleted after the receipt. New rows only. Until it lands, the limit "deploy holdback-op1 while no deal is mid-step" stays (`docs/operations.md:91`).
- **T-221 (PR 184 is slice 1), measured.** Slice 1 touches no `apps/demo-cloud` file, so after a deploy of slice 1 alone the live demo's `POST /v1/adjudicators` answers 404 (T-221 Handoff). Slice 2 adds the `ar:` rows (above). A registration's signature is checked under the node's domain (`apps/operator/src/registrations.ts`, `checkRegistration`), so registrations are bound to the rules contract: finding 4.

**Rollback under one world (inferred).** A `wrangler rollback` of both Workers reopens the same storage under the old code. The old code lists only its own prefixes, so it never reads `cursor`, `lane:` or `ar:`; `restore` structured-clones books, so `chainTxs` and `beaconSource` ride along unread; events written by the new code are read as data. Deals offered under the drand rulebook keep their book. The old adjudicator adapter seeds their fallback and appeal panels from the sim beacon, which the contract refuses, so those deals take the default outcome: today's limit. The old operator serves the sim rulebook again, so new offers bind the sim hash and are accepted. Money is unaffected: the chain holds it. T-220's rollback line should say this in place of "the previous world's view is no longer served".

### 4. A contract redeploy (T-212's open items; the gasless bond)

**Measured.**

- `world.ts:306` refuses to open a world against another rules address: "this world settles on the rules contract X, not Y (a new deployment needs a new world)". `LiveChain.check` refuses a contract under another domain version (`live.ts:218-222`). Both are deliberate (ADR-0028 §1, ADR-0029 §8).
- A new `HoldbackRules` is a new EIP-712 `verifyingContract` (`world.ts:320`, `holdbackDomain(chainId, rules)`), under which every message is signed and checked: offers, acceptances, agreements, decisions, appeals and mandates (`evm-settlement.ts:258, 656-658`), and T-221's registrations. Its constructor creates a new `HoldbackBonds` (`docs/backlog.md:19`, `docs/research/2026-11-04-adjudicator-registration.md` §4).
- The world holds one `chain: SimChain | EvmSettlement` for the operators, the adjudicators and the registry (`world.ts:270, 446, 476`), and `EvmSettlement` holds one deployment, one domain and one token (`evm-settlement.ts:247-265`).

**Inferred.**

- One world over two rules contracts needs: a settlement facade that routes each commitment to its deployment's `EvmSettlement`; a deployment per book; a domain per deployment in prepare and in every signature check; a `ChainSync` per contract; shared relayer lanes. A domain-version bump adds a harder problem: core's `holdbackDomain` has one version, so a new build cannot verify messages signed under the old one. Old deals would then be read-only plus the permissionless timeouts, which carry no signature. Estimate: days of adapter and operator work in the money path, plus a red-team pass. Not worth it for a testnet demo before mainnet, where a redeploy is a migration event in any case.
- So a contract redeploy is the one legitimate reason for a new world, and the rule should say so plainly. What a new world costs, in full: the API stops serving the old deals' state, events, ciphertexts (`ct:`) and judgment records (`jr:`), so a buyer who has not fetched its work cannot fetch it through the API; `/v1/events` restarts at seq 0 and `head.eventSeq` with it; the day lines' deal funnel restarts; faucet windows and mandates restart, so every address asks the faucet again and is re-admitted; registrations are gone, and outsiders re-sign under the new domain in any case.
- How history is kept when a world does change:
  1. **The chain.** Every funded step is a `HoldbackRules` log keyed by commitment id, and Etherscan shows it. The pre-funding stages, the envelopes and the deliverables are not on chain.
  2. **The old world's storage.** A rename deletes nothing; `worker.ts:54-58` and `docs/operations.md:74, 87` keep the old names for a rollback, which serves the old world again under the old code.
  3. **The deploy record** in `docs/operations.md` and the task's Evidence: the old world's name, rules address and deployment file (`contracts/deployments/sepolia-<date>-domain-<v>.json`), the new world's, the Worker versions, and the open deals at the switch with the timeouts someone sent.
  4. **Later, if wanted, a read-only archive.** The Worker forwards `GET /v1/commitments/{id}`, the ciphertext read and the judgment read to the previous worlds when the current one has no book. It needs the deployment file that matches each old world's `meta.rules`, and a build that opens an old-domain world read-only (skip `verify`, never send). Backlog, after round 1.
- The switch keeps T-220's "no deal left behind" rule: switch while no deal is open on the old world, or send its timeouts afterwards (anyone may) and record them.

**Monitoring (Rafa's reason).** No script or document in `docs/costs.md`, `docs/update-flow.md` or `agent-ops/` polls `/v1/status` or `/v1/events` today (measured by grep over those paths; the API monitor is planned work). When it exists it will read per-world state: the event sequence, `head.eventSeq`, the day lines' deal funnel, which the world computes from its own event log (`world.ts:513-525`). Those restart with a world. What does not: the Workers Logs lines (account-wide, 7 days), the Cloudflare analytics the cost collector reads, and the chain. One world keeps the per-world series continuous; a redeploy is the one planned break, and the deploy record marks it.

### 5. The demo adjudicators' keys and bonds

**Measured.**

- Keys derive from `meta.secret` and a label (`world.ts:308, 324`), so they live as long as the world.
- Bonds live in `HoldbackBonds` by address and token. `ensureBond` reads `bondOf` and sends nothing when the bond is there (`live.ts:401-417`); `meta.bonded` records which adjudicators are done (`world.ts:649-655`). The approve and deposit cost about 372,709 gas per adjudicator, and each gets 0.005 Sepolia ETH of gas money (`world.ts:145-148`); the three bonds took about two minutes at the 0.7 cutover (T-212 Handoff).
- T-221's registrations are signed under the domain, so they are bound to the rules contract, not to the world.

| Change | Keys | Bonds | Registrations (T-221) |
| --- | --- | --- | --- |
| Rulebook change | Same | Same | Same |
| Additive schema bump | Same | Same | Same |
| Code changes (T-217 to T-219, T-221) | Same | Same | Same; slice 2 creates the demo's three on its first open |
| Contract redeploy, new world (today's code) | New, random | Three new bonds in the new vault, about 1.12 million gas and 0.015 Sepolia ETH of gas money; the old vault keeps 75,000 tUSDC and the old addresses about 0.015 Sepolia ETH, behind keys no route can use | New, under the new domain |
| Contract redeploy, with a world key seed (below) | Same | Three new bonds in the new vault; the old vault's bonds stay withdrawable from the same keys | Re-signed under the new domain |

**Inferred.** The old vault's tUSDC is worthless and open-mint, and the stranded ETH is about 0.015 Sepolia ETH per world, so stranding is cosmetic. Continuity matters more: `llms.txt` and round 1's scenarios name the demo adjudicators by address. A world key seed, a Worker secret `WORLD_SECRET` on holdback-op1 made like `SEPOLIA_RELAYER_KEY` by a script that prints only the public addresses, would let a new world derive the same keys: `open` uses it for a new world's `meta.secret` and leaves a stored secret unchanged. About 20 lines plus a test. An option for Rafa; T-220 does not need it.

## Recommendation for T-220

Keep `holdback-public-demo-sepolia-2026-11-04`. The deploy:

1. **`apps/demo-cloud/src/world.ts`.** For the live world only, the rulebook names `randomness: { source: 'drand-quicknet', chainHash: DRAND_QUICKNET_CHAIN_HASH }` and each demo adjudicator gets `drand: drandQuicknet()` (T-217 Handoff). The "drand not yet" notice goes. `worker.ts` is unchanged.
2. **The fork run proves the in-place switch,** in place of a fresh world: open a test world with the sim rulebook and one open deal, then reopen it from the same storage under the new code, as `live.test.ts` reopens worlds. The old deal keeps its `rulebookHash` and moves on; an offer bound to the old hash gets 422 `rulebook_unknown`; the setup pass sends nothing (`bonded` stays at 3).
3. **Deploy both Workers together, then the site.** The order risk in the task file ("Deploying op2 first would open the new world under op1's old code") disappears with one world. The Durable Object still restarts when holdback-op1 deploys, so deploy while no deal is mid-step until T-219 lands.
4. **Record the rollback** as finding 3 states it: the same world under the old code; drand deals default on fallback and appeal; money unaffected.

Confidence: high on keeping the world through the rulebook change and the schema bump (measured); high that T-218 and T-221 fit one world (their authors wrote them for it); medium on the rollback reading (inferred, not run).

## Standing rule for later deploys

**A new world only for a new rules contract or another chain.** Everything else changes in place: rulebooks, additive schema versions, Worker code, judge registries, fees and, once the pin moves out of `meta`, windows.

When a new world is unavoidable:

1. Rafa approves the redeploy; it is a gate (`CLAUDE.md`, `docs/operations.md` Gates).
2. Switch while no deal is open on the old world, or send its timeouts afterwards and record them.
3. Record in `docs/operations.md` the old world's name, rules address and deployment file, the new world's, the Worker versions and the bonds' transactions.
4. Keep the old world's storage. Never delete a world.
5. With the key seed adopted, the new world derives the same adjudicator keys.
6. With the archive route built, it serves the old world's reads.
