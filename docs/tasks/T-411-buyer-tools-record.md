## Intent

The rehearsal on the live service (T-399) and the guide clean-up (T-401) left four small faults on the buyer's side. Each one costs a buyer's agent a wrong turn on its first deal:

1. When the faucet refuses a grant (429), `buy.mjs approve` dies with a stack trace. An agent cannot tell from that how long to wait, or whether money moved. It should stop with one plain line: the faucet's grants are used, it grants again in N seconds, nothing is paid.
2. The deal record on Sepolia lists the decision's transaction three times, because one transaction carries three events. It should list each transaction once. The payee (`row.paidTo`) stays empty on Sepolia because the chain's events carry no postings: fill it only if that is a small, tested read, else say what it takes.
3. The seller side once saw "operators disagree" 11 s after an offer, and the next poll went on. If the buyer's tools stop on one such read, an operator a few seconds behind the other stops a deal for nothing. A disagreement that clears within a short window should be read again, and one that does not clear must still stop: the two-operator check stays as strict as it is.
4. `llms.txt` names Node 20 for the try command, `buy.txt` Node 22.18 for the buyer's tools; and `buy.txt` step 9 reads as if running the checks yourself were a step, though it needs a clone the guide never sets up. State the Node version so an agent installs the right one first, and mark the clone step optional, inside the buyer's 5,000-token budget.

## Acceptance criteria

- [x] A faucet 429 on `approve` prints one line on stderr, with no stack trace: the faucet's grants are used, the seconds from `Retry-After` (or `retryAfterSec`), and that nothing is signed or paid; the exit status is 1, as `buy.txt` documents for a stop with nothing paid. A test that fails before the change shows it, through an operator that answers the faucet with 429.
- [x] `settlement.transactions` and `row.transactions` in the deal record list each transaction once, under the first step that names it. A test with three events on one transaction shows it.
- [x] `row.paidTo` on a chain: filled from a small, tested read, or left null with what filling it would take written in the Handoff.
- [x] The buyer's reads of what changes over time (the escrow state, the events, the balance, the released key) read again when the operators disagree, for up to about 15 s, and stop with the same `operators disagree on ...; do not proceed` when they still disagree. Reads of what does not change (the terms, discovery) stop at once, as now. Tests show a disagreement that clears, one that does not, and that another error is not retried.
- [x] `site/llms.txt` and `site/buy.txt` state the Node version once, so a buyer installs Node 22.18 or later first; step 9's own check is marked optional. Both guides stay ASCII; the buyer's path stays within 5,000 tokens (before and after measured by `node site/check.mjs`). The first paragraph of `llms.txt` after the tagline is unchanged, and "owner" stays "owner" in `buy.txt`.
- [x] `node site/build.mjs && node site/check.mjs` pass with nothing unexpected in `git status`; the old and new SHA-256 of `site/buy.mjs` are recorded, and `site/try.mjs` is unchanged.

**`row.paidTo` on a chain is not filled.** It is not a small read from the record's side. Two ways, in the order I would take them:
1. *The operators write the postings (recommended).* The contract's `PaymentReleased(jobId, provider, amount)` and `Refunded(jobId, client, amount)` logs (`contracts/src/IHoldbackRules.sol` lines 169 and 176) name the payee and the amount, but the EVM adapter writes `{}` as the payload of `settlement.released` and `settlement.refunded` (`packages/settlement/evm/evm-settlement.ts`, `payloadOf`, lines 1549 to 1552). If it wrote them as postings from `escrow:<id>`, together with the adjudication fee's transfer, `deal-record.ts` would fill `paidTo` and `refundedTo` and run its two postings checks with no change of its own. That is settlement code (kind 5, one review) and an operator deploy; it also changes what both operators serve, so both must run it before a record can rely on it. Not checked here: which log carries the adjudication fee's transfer.
2. *The record reads the chain.* A Sepolia RPC address (the chain pin carries none), `eth_getTransactionReceipt` for each decision transaction, and the token's `Transfer` logs out of the rules contract, checked against the pinned token. That is about 40 lines and a fake RPC in the test, and it breaks the record's promise that it sends GET requests only, only to the configured operators (`deal-record.ts` header, and its test "sends GET requests only ..."). Not small.
