# Outsider design tests, buyer-started (T-328, roadmap N1a), 2026-11-11

**The answer.** Four of four fresh agents reached the end state they were asked for from `https://crow.direct/llms.txt` alone, with no repository, no `try.mjs` and no hints [measured]. Only two of the four did it against Crow's live test seller as asked: scenarios 1 and 4 [measured]. Scenario 1 also had to drop the checks the agent chose and take the seller's own [measured]. Scenarios 2 and 5 are **blocked** against the test seller: it sells no rubric-judged work and cannot miss a deadline. In both, the agent found the block from the docs and the seller's card within a minute, asked, and then played both sides itself to the right end state [measured].

So `llms.txt` works for a buyer who builds its own client: every agent wrote a buyer from the docs and checked every message before signing it, and none needed the repository. The gaps are in what the test seller can play, one missing shape (the rubric criterion), and the doc's size.

## How the runs were made

- **The agent.** Claude Code 2.1.318 through the Agent SDK 0.3.318, model `claude-opus-5-5` at effort `medium`, the model and effort the headline metric names. The SDK's hooks reported `medium` in every run [measured].
- **What it got.** One sentence of goal naming `https://crow.direct/llms.txt` (the sentences are in `tools/one-click/outsider.mjs`, `GOALS`), an empty folder, Node 22.22.2, curl 8.7.1, default permissions, no settings files and no MCP servers. It made its own keys and took test tUSDC from the public faucet. No key of ours reached it.
- **The harness.** `tools/one-click/outsider.mjs`, built on the One-Click harness of PR 217 (T-066). It answers each permission request "allow" and counts it, answers a question card with its recommended option, and counts that too.
- **The sandbox.** The auto-mode classifier refused to start an agent whose tool requests the harness approves unsandboxed, which is T-066's gate 1 ("where the harness runs"). The four runs therefore ran with `--sandbox`: Claude Code's OS sandbox around every Bash command, with writes only in the agent's folders, no reads of this user's folders, and network only to Crow, npm and Sepolia hosts. Bash still asked each time. The sandbox cost some steps that a fresh machine would not take; "Harness effects" lists them, and the counts below include them.
- **Calls.** A `curl` wrapper on the agent's PATH logged every curl call and its status. From scenario 2 on, a `node` wrapper also logged every `fetch()` from the agent's scripts. In scenario 1 that probe did not load, because Claude Code drops `NODE_OPTIONS`, so its count covers curl only.
- **Run files.** `reports/scratch/t-328/<run>/` (`record.json`, `digest.jsonl`, `http.jsonl`, `sdk.jsonl`), not committed.

### Per scenario

1. **Dataset, own checks.** `llms.txt` worked [measured]. The agent proposed 7 checks: the seller's 3 plus unique email, an email format, no empty IDs and no hidden characters. The seller countered with its 3, and the agent's own client refused to fund the counter. The agent then asked; the harness picked "Adopt its 3 checks"; it funded and reached Released. It ran its 4 extra checks on the delivered file after the release, with no effect on payment. Commitment `0x5fb2aa43cde28617cc001b20c9fdd61e68ee3fea11a68e6f609f467bc8b7b78a`, Released and final. The part of the goal that says "checks you choose yourself" is blocked by the test seller (F3).
2. **Rubric-judged work.** Blocked against the test seller [measured]: its card offers one item, checks-only, and the docs say it refuses other work. The agent saw this in 30 s and asked; the harness picked "Play both sides". It then ran a `default`-template deal for a 223-word essay under a five-criterion rubric it wrote, and three live judges from two families (Anthropic and DeepSeek) passed it with a weighted score of 4.00 out of 4. Commitment `0x421232e8a45ab334a532051e7de10399d8aada086441d86c6fe61dc0a7ea1563`, Released. `llms.txt` worked for the rubric deal itself, apart from the criterion's shape (F4) [measured].
3. (Seller-started; not in this task.)
4. **Rejected delivery.** `llms.txt` worked with no gap [measured]. The agent used the documented `"test": {"outcome": "refund"}`, verified the offer on both operators, funded, and saw `rows` fail ("2 rows; expected 3 to 3"), a `reject` decision and no key released. ## Findings

Severity is for roadmap row N1a, "Outsiders can use it". None of these findings needs a change to the API or the contracts, so none is marked for the stage 4 spec [inferred]: each fix is in `site/llms.txt` or in Crow's test seller.

| --- | --- | --- | --- | --- |
| F1 | High | Crow's test seller; `llms.txt` "Crow's test seller", "What it sells" | An outside buyer cannot buy rubric-judged work from the test seller: its one offer is checks-only. Scenario 2 is blocked against it, so the judge panel, the part most specific to Crow, can only be tried by playing both sides [measured]. | A second offer on the test seller's card: a short text under the `default` template with a small rubric, judged by the live panel within its daily budget. |
| F2 | High | Crow's test seller; "Windows", "A refund on request" | An outside buyer cannot see a missed deadline with the test seller: it always delivers, offers no `silent` outcome, and its `deliverBy` is an hour after the offer. A buyer cannot show the buyer's burden of acceptance (D28) by writing stricter checks. In scenario 1 the agent's own client refused the counter, and the deal went ahead only after a question card [measured]. | Take a proposal whose checks the seller's delivery passes (it can run them with T-316's check runner before it offers), and counter only the rest. ### What worked without a gap [measured]

- **Discovery and the card.** Every agent found the test seller's card, its address and its fees, and checked `terms.seller` against the card.
- **Keys, sealing and signing.** Every agent made fresh keys, sealed its proposal to the intake key, and built and checked each EIP-712 message itself. Two of them ran the doc's crypto test vectors first.
- **The faucet and the fees.** Every buyer paid the right total, 30.71 tUSDC: the price, the 1 tUSDC adjudication fee and the 4.71 tUSDC operator fee.
- **Both operators.** Every agent read the offer from both `api.crow.direct` and `api2.crow.direct`. The agents in scenarios 1, 4 and 5 report that they recomputed the commitment ID and the funding nonces themselves.
- **Status codes.** No Crow call in any run answered 4xx or 5xx except the 4 early reclaims of F6.

## Harness effects (not doc gaps)

These came from the sandbox and the harness. A fresh machine would not hit them [inferred]. They are in the counts above.

- **The first Bash call in each run** failed with "allowed_domains cannot widen network access in this session". The agent retried at once without the parameter. That cost no approval.
- **TMPDIR.** Claude Code's sandbox sets `TMPDIR` to `/tmp/claude-501` and overrides the harness's own value. In scenarios 1 and 4 the agent saved `llms.txt` there, the harness denied a Read outside the agent's folder (3 denials in all), and the agent downloaded the doc again: about 2 approvals per run. A later harness should allow file tools under the sandbox's `TMPDIR`.
- **npm and Node in scenario 1.** npm could not write its home cache (2 approvals), and Node's `fetch` needed `NODE_USE_ENV_PROXY=1` to reach the sandbox's proxy (1 approval). Both were fixed in the harness before scenario 2.
- **GitHub.** The allowlist left out GitHub, so in scenarios 2 and 5 the agent's two calls to `raw.githubusercontent.com` and `api.github.com` failed (`CONNECT tunnel failed, response 403`). On an open machine those calls would have read the repository: scenario 2's agent was after the rubric example (F4), and scenario 5's searched the code for a test outcome [inferred].
- **Scenario 1's Node calls** were not counted (see "Calls" above).
- **The test seller's limit.** The runs used 2 of the seller's 3 requests per IP address an hour (scenarios 1 and 4).
