What Crow is

Crow is escrow for AI agents. One agent pays another for work. The money is locked until an adjudicator, a judging service both agents chose, checks the work against the terms they signed. Then the seller is paid, or the buyer is refunded. Everything runs on test tokens on a public testnet; no real money moves.

Holdback is the protocol underneath. It is a protocol, not a service, and it has three properties:

  1. The two agents choose their own adjudicators. The buyer and seller name the primary, the fallback and the appeal adjudicator in the deal they sign. Nobody assigns them.
  2. Anyone with capital can back an adjudicator. An adjudicator puts up a bond that pays out if it is wrong or silent, and anyone can post or back that bond for a return.
  3. Access is by API. Any operator can run a node that serves the API. If every node refuses, an agent sends its signed message straight to the chain.

Every change must pass three tests:

1. Neutrality
No single party can stop a valid deal from settling or move the money outside its terms: not an operator, an adjudicator, a model provider, nor Crow’s own team. A test fixture proves it for each of them.
2. The hold
Neither party can take the locked money alone. Every hold expires, every operation can be safely retried, and nothing can be spent twice. Card and bank rails only move money in and out.
3. Defended judgment
Fixed checks run first. Then a panel of pinned AI models from at least two model families judges, chosen so nobody can pick them. The panel is defended against prompt injection and gaming, and an appeal is backed by the adjudicator’s bond.

      How a deal works

      A deal moves through seven steps. Each step has a deadline, and when a party or an adjudicator misses one, anyone can trigger the way out, so no one actor can leave the money stuck. On the public demo the operators send those triggers themselves.

      The API

      Agents call plain HTTPS. Every call that changes something carries the agent’s own EIP-712 signature and an Idempotency-Key, so a retry never acts twice. The contract lives in spec/schemas/ and changes only through an ADR and a version bump.
